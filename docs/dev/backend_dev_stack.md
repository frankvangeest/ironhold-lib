# Local Nakama for development (`backend/`)

For engine developers working on the Nakama adapter, the server module or the online actions. A designer using the hosted web build does not need
this: the hosted projects use `fake://` or the public demo server.

**LOCAL ONLY. Default keys. Never deploy this.** The stack uses Nakama's default server key (`defaultkey`) and console login, a throwaway database
password and ports bound to `127.0.0.1`. Production and staging servers are configured in the homelab repo.

## How it is put together

```
backend/
  README.md            prerequisites, the run command, troubleshooting (read this first)
  .env                 pins only: NAKAMA_IMAGE, POSTGRES_IMAGE (the one place the engine repo pins the versions)
  docker-compose.yml   project `ironhold-dev`: nakama + postgres, 7350/7351 on 127.0.0.1, vendor healthcheck
  up.sh / down.sh      generate modules/, start/stop the stack
  modules/             generated by up.sh, gitignored
```

- `up.sh` runs `ironhold backend config` (the cached `tools/bin/ironhold`) to write `ironhold_games.lua`, then **copies the module source
  `crates/ironhold_nakama/server/ironhold.lua` over `modules/ironhold.lua`**, because the cached CLI embeds the module at its build time and can be stale.
  The module source stays in the crate: the CLI embeds it with `include_str!` (`crates/ironhold_nakama/src/server_config.rs`) and the CLI output, not a
  source path, is what a server admin (or the homelab deploy) uses.
- Default projects: every project under `assets/projects/` whose own `.project.ron` sets `backend_path` to a file name (a `fake://` project too, because a game must be on the server's list to
  sign in). Explicit arguments (folder names under `assets/projects/`) replace the default set. The CLI rejects duplicate `game_id`s.
- **One stack per machine.** Fixed ports and the project name `ironhold-dev`: several worktrees share the same server and database, whichever ran `up.sh` last owns the loaded modules, and `down.sh -v` from any worktree deletes the shared database.
- `up.sh` generates into a temporary folder and copies over `backend/modules/`, so a failure cannot leave it half-written; if the cached CLI's embedded module differs from the source it warns that the CLI is stale (the source module is used either way).
- **Re-running while up:** regenerates `modules/` and restarts only the `nakama` container (Nakama cannot reload modules); the Postgres container and the
  database volume are untouched. `down.sh -v` deletes the volume (all local accounts and scores).
- Every `docker compose` call passes `--env-file backend/.env` and runs from the repo root, so nothing depends on the working directory.
- `.gitattributes` pins `*.sh`, `*.yml` and `backend/.env` to LF: a carriage return inside a script or an image tag breaks them (the repo's other files are CRLF on Windows).

## Run a game against it

Needs Docker Desktop running and the cached CLI (build it once: see [What you need first](../../backend/README.md#what-you-need-first)). From the repo root:

```bash
backend/up.sh backend_demo
NAKAMA_SERVER_KEY=defaultkey cargo run -p ironhold_native -- --project backend_demo --backend http://127.0.0.1:7350
```

`--backend` replaces the endpoint in the project's `backend.ron`, and the file's `server_key` is **not** sent to a `--backend` server, so the key comes
from `NAKAMA_SERVER_KEY`. The hosted web build cannot use a local server: its endpoint comes only from `backend.ron`, and `?backend=` accepts only `fake://`.

## The contract test

`crates/ironhold_nakama/tests/contract/run.sh` tests the adapter and the module against a real Nakama. It reuses `backend/docker-compose.yml` under the project
name `ironhold-contract` and ports 7360/7361, with the fixture folder `tests/contract/modules/` mounted (an absolute path, passed in `NAKAMA_MODULES`), so it
can run while your dev stack is up and its cleanup (`down -v`) deletes only its own volume. The fixture `tests/contract/modules/ironhold_games.lua` stays where
it is: a unit test in `server_config.rs` embeds it.

`tests/contract/modules/test_rpcs.lua` is a test-only fixture: it registers probe RPCs through the module's `game_rpc` guard. It lives only in that mounted folder and is never part of `ironhold backend config` output or a deploy.

## Bumping the Nakama version

Change `NAKAMA_IMAGE` in `backend/.env`, run `crates/ironhold_nakama/tests/contract/run.sh`, then update the homelab's own pin and redeploy there.
