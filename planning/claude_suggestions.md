## UX / Designer footguns

- **Authoring a partial `inputs:` block (e.g. just to add `gamepad_index`) hard-fails RON parsing with a confusing "missing field `forward`" error** _(observed live-testing `gamepad_controller_input.md`'s demo wiring with a real controller, `6fb0f7e`, 2026-07-20)_ — `InputMap.forward`/`backward`/`left`/`right`/`strafe_left`/`strafe_right`/`jump` have no `#[serde(default)]`, unlike every other `InputMap` field (including all 5 new `gamepad_*` ones), so RON requires the whole struct to be present the moment a designer writes an `inputs:` block at all — there's no way to author "just this one field, keep the rest at default" for those 7 fields specifically. Hit this exact trap live: uncommenting `entity_logic_demo`'s own gamepad demo block (which only listed `gamepad_index` + the gamepad_* fields, per the plan's "uncomment and go" convention) broke scene load with `Unexpected missing field named "forward"`. Worth either giving those 7 fields WASD/Space defaults (closing the gap, matching every other field's ergonomics) or making the RON authoring guidance explicit that a *complete* `inputs:` block is required, not a partial override.

- **A single physical controller can register as two browser gamepad entries, one of them permanently dead — `gamepad_index: 0` isn't reliable** _(observed live-testing `gamepad_controller_input.md` with a real Xbox 360 controller, Windows 11 + Chromium-based browser, `6fb0f7e`, 2026-07-20)_ — confirmed via a temporary diagnostic system: entity `50v0` connected first and reported all-zero axes/buttons for the entire session even while the stick was actively moved; entity `51v0` connected second and showed live, correctly-changing data plus a real button press. Since `gamepad_index` is purely "connection order" (`resolve_gamepad` sorts by `Entity::index()` — see `runtime/input.rs`), index `0` landed on the dead duplicate. Documented as a troubleshooting tip in `docs/20_data_formats.md` (try index `1`/`2`), but the underlying fragility is real and pre-existing (this convention predates `gamepad_controller_input.md` — the feature only added button-name configurability on top of it, not the routing/sorting logic itself). Worth a future fix: detect and skip gamepad entries that report zero real analog resolution or a live/dead heuristic (e.g. prefer the entry the browser reports with `mapping: "standard"`, if gilrs exposes that), rather than relying on raw connection order.

- **Pad identity travels out-of-band from the `UiEvent` it's paired with — an intrinsic-pairing fix would be more robust than the current frame-scoped-resource approach** _(observed during `gamepad_hot_join.md`'s post-implementation review, debug-detective/system-architect, 2026-07-31)_ — `unclaimed_gamepad_trigger_system` writes a captured gamepad's identity into a separate `PendingJoinGamepad` resource alongside its `UiEvent::ButtonPressed`, relying on both being produced/consumed within the same frame and capped to one match total. This works (verified: emission is now also capped to one per frame, closing the double-join bug this same review found), but it's inherently fragile to future changes — e.g. `global_input_system` (keyboard) and `unclaimed_gamepad_trigger_system` (gamepad) are mutually unordered `UiEvent` writers, so a same-frame keyboard `G` + gamepad `South` press has nondeterministic event order, meaning the captured pad could end up bound to the keyboard-triggered joiner instead of the gamepad-triggered one. A `UiEvent` variant that carries its source (e.g. `UiEvent::GamepadButtonPressed(String, Entity)`) would let the interpreter/executor pair the pad with the exact event that produced it, rather than relying on frame-scoping + a one-match cap. Worth considering if a future feature needs a second source of gamepad-identity-carrying triggers, rather than re-deriving this same pattern each time.

## Correctness

- **`interactable_system`'s per-player fix makes a shared-interact-key double-fire newly reachable** _(observed fixing the local-coop `interactable_system` bug, debug-detective, `49eb9a2`, 2026-07-19)_ — the fix correctly makes interact work with 2+ players (previously dead entirely via `player_query.single()`), but since both `player_p1`/`player_p2` in `local_coop_demo` default to the same `"KeyF"` interact key, a single physical F press is seen as `just_pressed` by every player's loop iteration: if both players are in range of the same `Interactable`, `entity.interacted:{id}` now fires twice in one frame; if only one is in range, the other's press simultaneously emits a phantom `player.attack_missed`. Not a regression (interact was fully dead in multiplayer before), and no current project wires anything non-idempotent (a counter, toggle, or `OpenContainer`/`OpenShop`) to `entity.interacted` in a 2-player scene, so nothing currently misbehaves — but the semantics are worth a conscious decision (dedupe `entity.interacted` per frame? scope `player.attack_missed` per-player or drop it?) before any 2-player scene wires a non-idempotent action to it.

- **No validation guard against two players sharing the same `gamepad_index`** _(observed during `gamepad_controller_input.md`'s implementation, debug-detective, `6fb0f7e`, 2026-07-20)_ — `resolve_gamepad`'s `None`/out-of-range handling is safe, but if two player prefabs are authored with the same `Some(n)` `gamepad_index` (a plausible copy-paste mistake), both resolve to the *same* physical `Gamepad` entity — one button press now fires `interact`/`target_next` (and drives movement/turn/camera-pitch) for **both** players simultaneously, with no per-player attribution. `assemble_player_config` already warns on unrecognized gamepad button *names* (same seam); worth extending that same validation loop to warn on a duplicate `gamepad_index` across the player prefabs in one scene.

- **`interactable_system`'s `inventory_ui.panels_open > 0` gate is global, not per-player** _(observed during `gamepad_controller_input.md`'s scope-amendment sanity check, system-architect, `6fb0f7e`, 2026-07-20)_ — the whole system early-returns for *every* player the moment any one player has an inventory panel open, so in a 2-player scene, player 1 opening their inventory silently disables player 2's interact too. Predates this session's per-player fix and affects keyboard interact equally (not gamepad-specific); same global-vs-per-player class as the `player.attack_missed` entry above. Worth revisiting alongside that one the next time co-op interact feedback is touched.

- **This codebase has no test infrastructure for asserting "no warning was logged" — and the natural approach (a `tracing_subscriber` capture) doesn't work for Bevy's own internal error-handler warnings** _(observed while regression-testing the `target_indicator_system` double-despawn fix, 2026-07-19)_ — `bevy_ecs::error::handler::warn` (the handler Bevy's own command error-handling wires up by default) logs through the **old `log` crate facade** (`log::warn!`), not `tracing::warn!` directly; `LogPlugin` bridges `log` into `tracing` via `tracing_log::LogTracer` in a real running app, but no test in this suite runs `LogPlugin` (`setup_test_app` doesn't add it), so a `tracing_subscriber`-only capture (confirmed empirically: built one, it caught nothing) silently misses every Bevy-internal warning while still correctly catching this codebase's own `warn!`/`info!` call sites (which — need to double check — likely also route through the same `log` facade if they're plain `bevy::log::warn!` macro invocations, in which case *no* existing or future test can assert on *any* `warn!`/`error!` call site's log output without this same infrastructure). - **`Action::JoinPlayer` emits `coop.lobby_full` at enqueue time, not spawn-completion time** _(observed during local co-op hot-join implementation, system-architect + debug-detective review 2026-07-20)_ — the executor arm writes `GameEvent::Trigger("coop.lobby_full")` as soon as `next_slot + 1 == MAX_SPLIT_PLAYERS`, before `drain_spawn_queue_system` has actually spawned the joiner on a later frame. If an `Action::LoadScene` clears `PendingEntitySpawns` in between (the queued 4th join is discarded), `coop.lobby_full` already fired for a join that never happened. Narrow window (requires a `LoadScene` on the exact frame the cap-reaching join was queued) and low impact (the event only drives a cosmetic "lobby full" UI reaction in v1's demo, which doesn't even react to it yet — see the next entry). Fix if it matters in practice: emit from `drain_spawn_queue_system`'s `is_hot_join` branch after the increment, not from the executor arm.

- **`Action::JoinPlayer` + `Action::LoadScene` in the same executor pass can enqueue a stray hot-join against the outgoing scene** _(observed during local co-op hot-join implementation, debug-detective review 2026-07-20)_ — `LoadScene` clears `PendingEntitySpawns` synchronously but clears `ActiveSplitSlotCount`/`SceneHandleV2` via deferred `Commands`, so if the action order in one frame is `[LoadScene, JoinPlayer]`, the `JoinPlayer` arm still reads the pre-transition (stale) `active_split_slot_count`/`scene_handle` and pushes a hot-join `QueuedSpawn` indexing the *old* scene's `join_prefab_keys` after `LoadScene` already emptied the queue. Requires pressing the join key on the exact frame a portal `LoadScene` fires — very narrow. Worth a guard (e.g. also checking pending-load state in the `JoinPlayer` arm) only if this surfaces as a real, reproducible glitch.

- **`local_coop_demo/room8`'s always-visible join prompt doesn't demonstrate the recommended `coop.lobby_full` reaction pattern** _(observed during local co-op hot-join implementation, ux-gamedesigner-reviewer review 2026-07-20)_ — `docs/20_data_formats.md`'s hot-join section recommends reacting to `coop.lobby_full` by swapping a label's bound `GameVariable` text (since `SetEntityVisible` can't target a UI `Label`), but the shipped demo's `rules.ron` has no listener for `coop.lobby_full` at all — the event fires into the void and the "Press G to join" prompt stays visible forever, even at 4/4 players. Cheap polish: add a `( on: "coop.lobby_full", do_actions: [ SetVariable("join_prompt_text", "Lobby full!") ] )` rule + bind the label to it, so the canonical example actually teaches the documented pattern instead of just describing it.

- **`local_coop_demo/room8`'s P3/P4 control-hint label positions are copied from room6's 4-player quadrant layout without verifying they read correctly during the 2-player start** _(observed during local co-op hot-join implementation, ux-gamedesigner-reviewer review 2026-07-20)_ — the hints are static screen-space `Label`s (position doesn't track the live split layout), placed for the eventual 4-way grid. Whether they land sensibly relative to the *2-player* Grid subdivision before anyone joins hasn't been visually confirmed. Verify during playtest; if it reads oddly, either accept it (hints only matter once a player has actually joined that slot) or reposition for the 2-player state.

## Performance

- **`stat_label_update_system`/`world_stat_bar_update_system` allocate a `String` via `format!` before the change-detection guard, now 4x'd per split-screen scene** _(observed during Phase 4 of `split_screen_camera_followups.md`, wasm-perf-reviewer review 2026-07-12)_ — `capabilities/stat_display.rs`'s `world_stat_bar_update_system` (line ~190) and `stat_label_update_system` (lines ~276-282) both compute `format!(...)` unconditionally per entity every frame, before the `if text.0 != new_text` guard that gates the actual write — so the allocation itself is never skipped, even for `Visibility::Hidden` ranks whose value never changes. Phase 4's split-screen rank duplication means up to 4x these per-frame heap allocations in split scenes (worse for wave-spawned enemies with a `world_stat_bar` each — e.g. 50 fills → 200 `format!`/frame). Pre-existing pattern, only multiplied by this feature; the split-screen gate keeps ordinary single-camera scenes at zero change. Fix if profiling shows it matters: hoist a reusable buffer into a `Local<String>` and `write!` into it instead of `format!`, or skip the `format!` entirely for `Visibility::Hidden` instances.

- **`target_hud_update_system` allocates a `format!` string every frame per active split camera, uncached** _(observed during Phase 1 of `per_player_split_screen_targeting.md`, wasm-perf-reviewer review 2026-07-13)_ — same class as the `stat_display.rs` entry above: `camera.rs`'s `target_hud_update_system` computes `format!(...)` for the readout text every frame a player has a target selected, not cached in a `Local` and not skipped when the target id is unchanged from last frame — only the downstream `Text`/`Node`/`Visibility` writes are guarded. Correctly skips the allocation when the player has no target (early-returns to `Visibility::Hidden` first). Capped at ≤`MAX_SPLIT_PLAYERS` (4) small strings/frame — negligible today, lower priority than the stat_display case since it's not multiplied by wave-spawn counts. Fix alongside the stat_display entry for consistency if that one is ever addressed: cache the last-rendered target id in a `Local`/component field and skip `format!` when unchanged.
