## UX / Designer footguns

- ~~**Authoring a partial `inputs:` block (e.g. just to add `gamepad_index`) hard-fails RON parsing with a confusing "missing field `forward`" error**~~ _(observed live-testing `gamepad_controller_input.md`'s demo wiring with a real controller, `6fb0f7e`, 2026-07-20; re-confirmed still open and promoted to `planning/backlog.md` ▸ Engine / Runtime, 2026-08-31)_ — `InputMap.forward`/`backward`/`left`/`right`/`strafe_left`/`strafe_right`/`jump` have no `#[serde(default)]`, unlike every other `InputMap` field (including all 5 new `gamepad_*` ones), so RON requires the whole struct to be present the moment a designer writes an `inputs:` block at all — there's no way to author "just this one field, keep the rest at default" for those 7 fields specifically. Hit this exact trap live: uncommenting `entity_logic_demo`'s own gamepad demo block (which only listed `gamepad_index` + the gamepad_* fields, per the plan's "uncomment and go" convention) broke scene load with `Unexpected missing field named "forward"`. Worth either giving those 7 fields WASD/Space defaults (closing the gap, matching every other field's ergonomics) or making the RON authoring guidance explicit that a *complete* `inputs:` block is required, not a partial override.

- **A single physical controller can register as two browser gamepad entries, one of them permanently dead — `gamepad_index: 0` isn't reliable** _(observed live-testing `gamepad_controller_input.md` with a real Xbox 360 controller, Windows 11 + Chromium-based browser, `6fb0f7e`, 2026-07-20)_ — confirmed via a temporary diagnostic system: entity `50v0` connected first and reported all-zero axes/buttons for the entire session even while the stick was actively moved; entity `51v0` connected second and showed live, correctly-changing data plus a real button press. Since `gamepad_index` is purely "connection order" (`resolve_gamepad` sorts by `Entity::index()` — see `runtime/input.rs`), index `0` landed on the dead duplicate. Documented as a troubleshooting tip in `docs/20_data_formats.md` (try index `1`/`2`), but the underlying fragility is real and pre-existing (this convention predates `gamepad_controller_input.md` — the feature only added button-name configurability on top of it, not the routing/sorting logic itself). Worth a future fix: detect and skip gamepad entries that report zero real analog resolution or a live/dead heuristic (e.g. prefer the entry the browser reports with `mapping: "standard"`, if gilrs exposes that), rather than relying on raw connection order.

- **Pad identity travels out-of-band from the `UiEvent` it's paired with — an intrinsic-pairing fix would be more robust than the current frame-scoped-resource approach** _(observed during `gamepad_hot_join.md`'s post-implementation review, debug-detective/system-architect, 2026-07-31)_ — `unclaimed_gamepad_trigger_system` writes a captured gamepad's identity into a separate `PendingJoinGamepad` resource alongside its `UiEvent::ButtonPressed`, relying on both being produced/consumed within the same frame and capped to one match total. This works (verified: emission is now also capped to one per frame, closing the double-join bug this same review found), but it's inherently fragile to future changes — e.g. `global_input_system` (keyboard) and `unclaimed_gamepad_trigger_system` (gamepad) are mutually unordered `UiEvent` writers, so a same-frame keyboard `G` + gamepad `South` press has nondeterministic event order, meaning the captured pad could end up bound to the keyboard-triggered joiner instead of the gamepad-triggered one. A `UiEvent` variant that carries its source (e.g. `UiEvent::GamepadButtonPressed(String, Entity)`) would let the interpreter/executor pair the pad with the exact event that produced it, rather than relying on frame-scoping + a one-match cap. Worth considering if a future feature needs a second source of gamepad-identity-carrying triggers, rather than re-deriving this same pattern each time.

## Correctness

- **`interactable_system`'s per-player fix makes a shared-interact-key double-fire newly reachable** _(observed fixing the local-coop `interactable_system` bug, debug-detective, `49eb9a2`, 2026-07-19)_ — the fix correctly makes interact work with 2+ players (previously dead entirely via `player_query.single()`), but since both `player_p1`/`player_p2` in `local_coop_demo` default to the same `"KeyF"` interact key, a single physical F press is seen as `just_pressed` by every player's loop iteration: if both players are in range of the same `Interactable`, `entity.interacted:{id}` now fires twice in one frame; if only one is in range, the other's press simultaneously emits a phantom `player.attack_missed`. Not a regression (interact was fully dead in multiplayer before), and no current project wires anything non-idempotent (a counter, toggle, or `OpenContainer`/`OpenShop`) to `entity.interacted` in a 2-player scene, so nothing currently misbehaves — but the semantics are worth a conscious decision (dedupe `entity.interacted` per frame? scope `player.attack_missed` per-player or drop it?) before any 2-player scene wires a non-idempotent action to it.

- ~~**No validation guard against two players sharing the same `gamepad_index`**~~ _(observed during `gamepad_controller_input.md`'s implementation, debug-detective, `6fb0f7e`, 2026-07-20; fixed by `gamepad_player_binding_hardening.md`, 2026-08-01)_ — `resolve_gamepad`'s `None`/out-of-range handling was safe, but two player prefabs sharing the same `Some(n)` `gamepad_index` resolved to the *same* physical `Gamepad` entity with no per-player attribution. Now caught both by a scene-load `warn!` (`scene_loader.rs::warn_duplicate_gamepad_index`) and a hard `ironhold_cli validate` error (`duplicate_gamepad_index`), scoped to a scene's instantiated `entities:` list.

- ~~**Duplicate-`gamepad_index` detection doesn't cover `join_prefab_keys` prefabs**~~ _(observed during `gamepad_player_binding_hardening.md`'s post-implementation review, debug-detective, 2026-08-01; re-confirmed still uncovered and promoted to `planning/backlog.md` ▸ Designer Experience, 2026-08-31)_ — both `scene_loader.rs::warn_duplicate_gamepad_index` and the matching `ironhold_cli validate` check only iterate a scene's already-instantiated `entities:` list, never `scene.join_prefab_keys`. A join prefab authoring a `gamepad_index` that collides with a scene-authored player produces no design-time diagnostic at all — the collision only surfaces at runtime, 3 seconds after a gamepad join, via `gamepad_bind_system`'s "resolves to a controller already bound to another player" warn. Latent today (no shipped `join_prefab_keys` prefab authors a `gamepad_index`), but the CLI's `validate.rs` already has a `join_prefab_keys` validation loop (checks tags/kind) that the duplicate check could extend into cheaply.

- **`gamepad_bind_system`'s cross-player invariant relies on every `BoundGamepad`-writing spawn path independently avoiding a duplicate, rather than self-healing** _(observed during `gamepad_player_binding_hardening.md`'s post-implementation review, system-architect, 2026-08-01)_ — after fixing the two concrete leaks found in review (the hot-join in-flight-spawn hole and the `FixedUpdate`-vs-`Update` one-frame lag in `unclaimed_gamepad_trigger_system`), there is no currently-known path to two players ending up bound to the same pad. But the invariant is still enforced by each writer separately getting it right, not by `gamepad_bind_system` itself detecting and correcting a duplicate if one ever appears (e.g. from a future third spawn path). Worth adding, as pure defense-in-depth: each pass, reconcile any already-bound duplicates by keeping the lowest `PlayerIndex` and resetting the rest to pending with a one-shot `warn!` — cheap (one extra branch in a loop that already visits every bound player for the disconnect diagnostic) and makes the guarantee hold regardless of how a duplicate got introduced.

- **`interactable_system`'s `inventory_ui.panels_open > 0` gate is global, not per-player** _(observed during `gamepad_controller_input.md`'s scope-amendment sanity check, system-architect, `6fb0f7e`, 2026-07-20)_ — the whole system early-returns for *every* player the moment any one player has an inventory panel open, so in a 2-player scene, player 1 opening their inventory silently disables player 2's interact too. Predates this session's per-player fix and affects keyboard interact equally (not gamepad-specific); same global-vs-per-player class as the `player.attack_missed` entry above. Worth revisiting alongside that one the next time co-op interact feedback is touched.

- **Runtime `warn!` and `ironhold_cli validate` report different collision pairs when 3+ slots collide on the same key/button** _(observed during `gamepad_action_bar_slots.md`'s review, debug-detective + system-architect, 2026-07-31)_ — the runtime's `seen.get()`-then-insert-only-when-absent pattern always cites the *first* colliding slot in every subsequent warning (A↔B, then A↔C), while the CLI's `seen.insert()` (which overwrites) cites the *previous* one each time (A↔B, then B↔C). - **A player-authored `stat_label`/`world_stat_bar` pushed during the terrain-delayed spawn path could see a stale (pre-split) `ActiveSplitScreen`/`DynamicSplitConfig` and skip rank-duplication in a split-screen + terrain scene** _(observed at player_stat_widgets.md implementation, debug-detective, 2026-07-17)_ — `spawn_player_entity_core`'s `DynamicStatUiEntry` push is an immediate `ResMut` mutation, visible to `drain_dynamic_stat_ui_system` the same frame; `spawn_players_and_camera`'s `ActiveSplitScreen`/`DynamicSplitConfig` inserts are deferred `commands.insert_resource` calls. ## Performance

- **`stat_label_update_system`/`world_stat_bar_update_system` allocate a `String` via `format!` before the change-detection guard, now 4x'd per split-screen scene** _(observed during Phase 4 of `split_screen_camera_followups.md`, wasm-perf-reviewer review 2026-07-12)_ — `capabilities/stat_display.rs`'s `world_stat_bar_update_system` (line ~190) and `stat_label_update_system` (lines ~276-282) both compute `format!(...)` unconditionally per entity every frame, before the `if text.0 != new_text` guard that gates the actual write — so the allocation itself is never skipped, even for `Visibility::Hidden` ranks whose value never changes. Phase 4's split-screen rank duplication means up to 4x these per-frame heap allocations in split scenes (worse for wave-spawned enemies with a `world_stat_bar` each — e.g. 50 fills → 200 `format!`/frame). Pre-existing pattern, only multiplied by this feature; the split-screen gate keeps ordinary single-camera scenes at zero change. Fix if profiling shows it matters: hoist a reusable buffer into a `Local<String>` and `write!` into it instead of `format!`, or skip the `format!` entirely for `Visibility::Hidden` instances.

- **`target_hud_update_system` allocates a `format!` string every frame per active split camera, uncached** _(observed during Phase 1 of `per_player_split_screen_targeting.md`, wasm-perf-reviewer review 2026-07-13)_ — same class as the `stat_display.rs` entry above: `camera.rs`'s `target_hud_update_system` computes `format!(...)` for the readout text every frame a player has a target selected, not cached in a `Local` and not skipped when the target id is unchanged from last frame — only the downstream `Text`/`Node`/`Visibility` writes are guarded. Correctly skips the allocation when the player has no target (early-returns to `Visibility::Hidden` first). Fix alongside the stat_display entry for consistency if that one is ever addressed: cache the last-rendered target id in a `Local`/component field and skip `format!` when unchanged.
