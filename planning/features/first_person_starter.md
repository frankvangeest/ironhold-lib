# Feature: First-Person Shooter Starter Demo (`first_person_starter`)

_Status: Draft (plan-reviewed 2026-10-16; all review decisions made, see "Decisions made" at the end of this file; becomes Ready once the plan body is edited to match and the cursor-capture spike result is recorded)_
_Planned at: `eb56cf3` (2026-10-16)_

## Phases

| Phase | Backlog item | Status | Completed |
|---|---|---|---|

## What
A new example project, `first_person_starter`, that a designer copies as the starting point for a first-person shooter. The player is the male character (`character-male-01.glb`) seen through a `FirstPerson` camera with a centre crosshair, in a small test arena with shootable targets. Keyboard + mouse and a gamepad both work from the first frame, in the same session, with no mode switch. v1 is the movement/look feel; v2 adds aiming and firing so there is something to shoot at.

Nothing about the shooter is hardcoded in Rust: bindings, look speeds, aim range, damage, cooldown, sounds and effects are all RON. The engine only gains the generic mechanisms a first-person game needs and a third-person game does not.

## Why
`camera_modes` already has a `FirstPerson` room, but it is a camera smoke test (capsule, mouse look, WASD) and not a usable game starting point. Making it into one exposes real gaps, found by reading the code at `eb56cf3` (this is what the backlog item's open questions turned into):

| Question | Finding |
|---|---|
| Does first-person look work on a gamepad? | **Yaw only, indirectly.** `first_person_camera_system` (`capabilities/camera.rs:577-623`) reads `MouseMotion` only: it rotates the player `Transform` for yaw and keeps pitch on the camera mode state. The right stick X already feeds `InputAction::Turn` (`runtime/input.rs:375-377`), which rotates the character at `rot_speed` (`capabilities/player.rs:573-596`), an unrelated tank-turn rate. Right stick **Y has no first-person consumer** (only the Orbit system reads it, `camera.rs:270-276`). So there is no gamepad pitch. |
| Do A/D strafe? | **No by default.** A/D emit `Turn` unless `strafe_mouse_button` is held (`input.rs:335-364`). `InputMap.strafe_left/right` (Q/E) are defined but I found no reader of them in `src` (`grep strafe_left` hits only `schema/player.rs`). An FPS needs A/D to strafe and the mouse to turn. |
| Is sprint hold-to-run? | **No, a toggle.** Every `Run` press flips `is_running` (`player.rs:576-578`). FPS convention is hold. |
| Is there a projectile or hit-scan primitive? | **No.** No match for projectile/hitscan/raycast-fire in `crates/`. Rapier `cast_ray` is already used for NPC line of sight (`capabilities/npc.rs:139`), so the physics access pattern exists. |
| How does combat work today? | An action-bar slot's `do_actions` run against `{target}`, the player's `PlayerTarget` (e.g. `ModifyStat(key: "{target}.health", ...)`, `SpawnEffect`, `EmitEvent("entity.attacked:{target}")`, see `3rd_person_game_demo/scenes/main.scene.ron:437-446`). Cost, cooldown and `{target}` gating are device-agnostic. Target selection is screen-space proximity to the **mouse cursor** (`targeting.rs`), which an FPS does not have. |
| Can a slot be fired by a mouse button? | **No.** `ActionSlotDef.key` documents "Not supported: mouse buttons" (`schema/scene_v2.rs:1434`). `gamepad_key` already accepts `RightTrigger2` etc. (`schema/player.rs:573-576`). |
| Is the cursor captured? | **No.** Nothing in `crates/` references `CursorGrabMode`/`cursor_options`. In a browser, mouse look without pointer lock stops at the canvas edge, and the cursor stays visible. |
| Is there a crosshair? | No dedicated node. `UiNodeDef` has `Rect`, `Label`, `Group`, buttons, panels. A crosshair is authorable from `Rect`s in a centred `Group` (**verify** centring works as expected before relying on it). |
| Own body in view? | The camera sits at `eye_offset` inside the player. A GLB body would clip through the near plane and show the inside of the head. `Action::SetEntityVisible` exists, and Bevy visibility inherits to children, so hiding the player entity should hide the whole model (**verify**, including that the camera entity is not a child). It also drops the body's shadow, acceptable for v1. |
| Pause? | First-person mouse look already gates on `sim.is_running()` (`camera.rs:600-602`), so any new look input joins that gate. |

## Approach

### v1: control scheme and project

1. **Control schemes with per-binding override (revised after UX consult 2026-10-16; replaces the earlier `movement_style` idea).** Frank's principle: the game creator can always override any binding. Layering, in order: **a field the designer wrote, then the scheme's default, then the engine default.**
   - `InputMap.controls: ThirdPerson | FirstPerson` (unquoted enum, `velocity_curve: EaseOut` style; not called `preset`, which `camera_modes` already uses for scene registry entries). `ThirdPerson` is the default and reproduces today's behaviour exactly, including `strafe_mouse_button: "Left"`. `FirstPerson` defaults: A/D = strafe, no turn keys, right stick = look (does not emit `Turn`), hold-to-sprint. `SideScroll` is **not** in the enum: it needs different movement (fixed world axis, locked depth), not just different keys, so a keys-only variant would mislead. Add it when the movement code supports it.
   - **Bindings become actions:** `left`/`right` mean *turn* (names kept for compatibility, docs say turn), `strafe_left`/`strafe_right` actually strafe (they are read by nothing today). Every key field becomes `Option<String>` so `None` unbinds; `implicit_some` is on (`ron_loader.rs:98`) so existing `left: "KeyA"` lines still parse unchanged. `""` stays a footgun today and should warn.
   - **Layer split:** what keys and sticks do (turn vs strafe, right stick, sprint mode) belongs to `InputMap`/`controls:`; how look feels (`gamepad_look_speed`, `invert_y`, `capture_cursor`) belongs to `FirstPersonCameraDef`. `controls:` never sets camera fields.
   - Authored example: `inputs: ( controls: FirstPerson, run: "ShiftRight", strafe_left: None )`.
   - **Must fix in the same change (verified):** the shipped projects already write `strafe_left/right: "KeyQ"/"KeyE"` into prefabs (`3rd_person_game_demo`, `camera_modes`, `local_coop_demo`) that do nothing today; once wired, `3rd_person_game_demo`'s player strafes on **E** while `main.scene.ron:509` has an action-bar slot on `key: "KeyE"`. "Existing projects byte-identical" therefore only holds if those Q/E lines are removed or set to `None` for `ThirdPerson` (or the old behaviour kept by making `ThirdPerson` ignore strafe keys, which is the worse answer: it keeps the dead fields). Audit every project's slot keys against its strafe keys. The docs rows at `docs/20_data_formats.md:2265-2266` currently claim these keys work and need correcting.
   - **Validate/CLI:** warn when `controls:` does not match the player's camera mode (`FirstPerson` with an Orbit camera, `ThirdPerson` with a `FirstPerson` camera), when one key is bound twice in an `InputMap`, when a movement key equals an action-bar slot key in a scene using that prefab, and on unknown key names (today they silently unbind). `ironhold inspect`/`query` prints each effective binding with its source: `authored`, `scheme:FirstPerson` or `default`.
   - Changed in `input_translator_system` and schema; `player_movement_system` is untouched.
2. **Gamepad look in `first_person_camera_system`.** Read right stick X (yaw) and Y (pitch) through the owning player's `Option<&BoundGamepad>` via `CameraTargets` (same lookup `camera_orbit_system` uses; **never a required `&BoundGamepad`**, see `capabilities/CLAUDE.md`). New `FirstPersonCameraDef` fields: `gamepad_look_speed: f32` (rad/s, default `2.5`), `invert_y: bool` (default `false`, applies to mouse and stick). Rate is dt-scaled on the **sim** clock, unlike mouse delta, and sits behind the same `sim.is_running()` gate. Keyboard look reuses the existing `InputMap.look_left/right/up/down` fields (they are currently Orbit-only), so keyboard-only players without a mouse can still look. Pitch sign is pinned by a regression test, like Orbit's (`camera.rs:253-261`), not asserted from hardware feel. Yaw is written to the player `Transform` exactly like the mouse path does today, so mouse and stick compose.
3. **`InputMap.run_mode: Toggle | Hold`** (default comes from the scheme: `Toggle` for `ThirdPerson`, `Hold` for `FirstPerson`; still overridable by writing the field). `Hold` emits `InputAction::Run(held)` every tick and `player_movement_system` sets `is_running = held` for that mode; the toggle path is unchanged.
4. **Cursor capture: `FirstPersonCameraDef.capture_cursor: bool`** (default `false`, so the existing `camera_modes` room is unchanged). When true: grab and hide the cursor on the first canvas click (browsers require a user gesture for pointer lock), release it while any `SimClock` hold is active (pause menu, focus loss) so UI is clickable, re-grab on the next click after resume, and release on `SetCameraMode` away from first person and on `LoadScene` into a scene without it. Cosmetic window state, never pushes to `ActionQueue`. Native and WASM both go through Bevy's `CursorOptions` (`grab_mode`/`visible`). **Spike first** (Task 1): confirm it works on WebGPU in Chrome/Edge, and what happens on Escape (the browser releases pointer lock itself and the engine must notice and treat it like pause or an unlocked state, not fight it).
5. **Project `first_person_starter`** (`/new-project first_person_starter`, never hand-copied). Scenes: `main` (the arena). Assets: the project's own `assets.ron` entries for `character_male` (`shared/models/characters/character-male-01.glb#Scene0`) plus the `animation_sources` the `3rd_person_game_demo` player uses, so the `player_male` rig and clips resolve, and `overrides/model_fixes.ron` if the male model needs the same fix. Prefab `player_male_fps`: `camera_mode: FirstPerson(eye_offset ≈ (0, 1.65, 0), fov 90, capture_cursor: true, gamepad_look_speed ...)`, `inputs: (controls: FirstPerson, gamepad_index: 0, ...)` (`run_mode: Hold` comes from the scheme; `gamepad_index` must be set for a single-player gamepad to work at all, so the `gamepad_index` doc row's "Local co-op only" label is corrected too), hidden own body via `SetEntityVisible` on `scene.ready`. Crosshair: a centred `Group` of small `Rect`s. Arena from primitives: floor, perimeter walls, a few cover boxes, a ramp or two steps (to exercise jump and slope handling), `training_dummy` targets placed at several ranges. A short `Label` hint lists the bindings for both devices.
6. **Bindings table** (to document on the scene and in the README row):

| Action | Keyboard + mouse | Gamepad |
|---|---|---|
| Move | WASD | Left stick |
| Look | Mouse (keyboard look keys as a fallback) | Right stick (X yaw, Y pitch) |
| Jump | Space | South (A) |
| Sprint (hold) | Shift | East (B) |
| Fire (v2) | Left mouse | Right trigger (`RightTrigger2`) |
| Aim down sights (later) | Right mouse | Left trigger |
| Interact / pause | F / Escape | West (X) / Start |

### v2: aim targeting and fire

The combat pipeline already exists (`{target}`, slot cost/cooldown, `ModifyStat`, `ShowDamagePopup`, `SpawnEffect`). What is missing is **who the target is when there is no cursor**, and a fire input that is not a keyboard key. So v2 adds two small generic mechanisms and **no weapon system**:

1. **`FirstPersonCameraDef.aim_target: Option<AimTargetDef>`** with `range` (default `40.0`), `radius_px` (default `48.0`, size of the crosshair catch circle) and `require_line_of_sight` (default `true`). When set, a new `aim_target_system` drives that player's `PlayerTarget` each frame from the **viewport centre** instead of the mouse cursor: among `targetable` entities within `range` and `radius_px` of the centre, pick the nearest to the centre (same screen-space projection and `select_aim_height` as `click_select_system`), then, if `require_line_of_sight`, cast **one** Rapier ray from the camera to it (`exclude_sensors()`, ignore the player's own collider) and drop the target if something else is hit first. Everything downstream (`{target}`, `target.changed`, the HUD variables, indicator ring) keeps working unchanged, so a shot slot is just today's slot RON. `click_select_system` and `tab_targeting_system` skip a player whose camera has `aim_target` (left click is now "fire", and a stray click-to-clear would fight the crosshair). **Ordering hazard:** this system writes `PlayerTarget`, so it must be placed explicitly in the `GameStreamSet::Targeting` chain per `capabilities/CLAUDE.md` ("Targeting systems are ordered on purpose"), after `tab_targeting_system` and `target_auto_clear_system`, before `GameStreamSet::ActionBar`; extend `tests/schedule_order_tests.rs` coverage.
2. **Mouse buttons as a slot `key`**: extend the slot key parser to accept `"MouseLeft"`, `"MouseRight"`, `"MouseMiddle"` (read from `ButtonInput<MouseButton>`, `just_pressed`, same fire path as keyboard, collapsing with it into one activation per frame). Gamepad needs no change (`gamepad_key: "RightTrigger2"`). v2 is **semi-auto**: one shot per press, bounded by the slot's `cooldown_secs`. Hold-to-repeat is deferred (below). The key string stays the slot's identity, so events are `action_bar.pressed:MouseLeft`. Guard against the engine's existing UI-click path: with the cursor captured there is no pointer over the slot `Button`, so no double fire; test it.
3. **Shot RON** lives in the scene's action bar (or a hidden one if a visible bar is unwanted: **verify** an `ActionBar` can be non-visual, else give it a tiny ammo-style HUD strip), e.g. `PlaySound(key: "shot")`, `ModifyStat(key: "{target}.health", delta: -25.0)`, `ShowDamagePopup`, `SpawnEffect(key: "hit_spark", entity: "{target}")`, `EmitEvent("entity.attacked:{target}")`. A shot with no target does **nothing** (the slot is `{target}`-gated, `action_needs_target`), so there is no muzzle flash on a miss in v2; flagged under Open questions.
4. **Training dummies**: prefab with `targetable: true`, an entity-scoped `{self}.health` stat, and a small behavior file that goes to a "down" state at 0 health and respawns via `SetDespawnTimer`/spawn (not `EmitEventAfterDelay` + `Despawn`, whose stale timers survive `LoadScene` and can hit a reused id, see the Delayed-events Bug and `capabilities/CLAUDE.md`). Model the wiring on `enemy_zombie.behavior.ron` after reading it.

## Out of scope (logged as follow-ups when v2 lands, not part of this plan)
Ammo and reload, hold-to-repeat fire, recoil and spread, weapon view-model (hands/gun mesh attached to the camera), aim-down-sights zoom (a `fov` change via `SetCameraMode` preset), hit-marker and damage-direction HUD, enemy AI that shoots back, shadow-only own body, pick-ups, multiple weapons and weapon switching, **local co-op / split-screen first person** (one shared mouse cannot drive two first-person cameras, same limit as Orbit's `orbit_button: "None"` rule), input remapping UI (already queued separately), `Fixed`-tick sim for the shot (aim runs in `Update` like targeting, deliberately).

## Risks
- **Pointer lock on the web** is the main unknown. It needs a user gesture, behaves differently across browsers, and cannot be exercised by the headless suite; the playtest is manual (`python serve.py` in the worktree), and Playwright `--real-gpu` only covers the static baseline. Port rule from memory: use a different port for `test_web.py` than a manual `serve.py`.
- **`first_person_camera_system` writes the player's `Transform` rotation** from per-frame input while physics runs in `FixedUpdate`: adding a second yaw writer (stick) in the same system keeps one writer, but any change must not touch yaw from `player_movement_system` for `Strafe` players, or two writers fight.
- **Hidden body = no body shadow and no nameplate/stat bar** on the player (the world stat bar the male prefab carries in `3rd_person_game_demo` is not copied).
- **Aim system cost**: one projection pass over `targetable` entities and at most one ray per frame per aiming player, only when `aim_target` is set; negligible next to existing targeting, but `wasm-perf-reviewer` should confirm.
- **Gamepad quirks** already logged (`Web gamepad robustness`, stick drift/deadzone) apply as-is; v1 reuses `InputMap.gamepad_deadzone`.

## Open questions (recommendation first)
1. **Where does the strafe/look switch live?** Resolved for now (Frank + UX consult 2026-10-16): `InputMap.controls: ThirdPerson | FirstPerson` supplying defaults only, with every binding overridable and `None` to unbind (see v1 approach item 1). The dead Q/E fields are fixed in a separate prerequisite item (decided 2026-10-16): `planning/features/input_strafe_bindings.md`.
2. **Should the engine own cursor capture at all in v1, or can v1 ship without it?** Recommend yes, but only behind `capture_cursor` and only after the spike; a mouse-look FPS without it is poor on the web.
3. **Should a shot with no target do anything?** Recommend v2 accepts "nothing" (it falls out of the existing `{target}` gating) and v3 adds a `fire` slot variant that always runs its actions with `{target}` optional (muzzle flash, ammo use, miss tracer). The alternative is to make that change in v2, which widens it into the action-bar code.
4. **Use hit-scan via the existing `PlayerTarget`, or add a true `Action::HitscanFire` / projectile?** Recommend the former for the *starter*: it needs no new `Action` (so no four-site `{self}`/`{target}` substitution work), keeps all damage in RON, and fits "a starting point". A projectile or ballistic weapon is its own feature (needs fixed-tick physics, determinism and pooling decisions).
5. **Own-body handling:** recommend hide-the-whole-player for v1; a proper "hidden from owner, visible to others/shadows" mechanism waits for a multiplayer or mirror use.
6. **Mouse-button slot key vs. a dedicated `fire:` field on `InputMap`.** Recommend extending the slot `key` (no new concept, keeps `action_bar.*` events and cooldown/cost). Only if the `ActionBar` UI cannot be made non-visual cleanly should a separate fire binding be reconsidered.

## Acceptance criteria
v1
- Given `first_person_starter` is loaded with keyboard and mouse, when the player uses WASD, the mouse and Space/Shift, then they strafe, look in yaw and pitch (pitch clamped), jump and sprint only while Shift is held; A/D never turn the character.
- Given a gamepad is connected, when the left stick moves and the right stick looks, then movement and yaw/pitch look work with no keyboard or mouse input, stick drift below the deadzone does nothing, and pushing the stick up looks up (inversion only with `invert_y`).
- Given both devices are used in the same session, then neither blocks the other and the HUD hint is accurate for both.
- Given the simulation is paused (or the window loses focus), then look input does not rotate the player and the cursor is released and visible; on resume and a click, capture resumes.
- Given an existing project that omits the new fields (`camera_modes`, `3rd_person_game_demo`), then behaviour is byte-identical (defaults), proven by the existing suites passing unchanged.
- Given the male model, then the player's own body is not visible from the camera and nothing clips through the near plane.

v2
- Given the crosshair is over a `targetable` target in range and unobstructed, then that target is the player's `PlayerTarget`, `{target}` resolves to it, and the target HUD variable names it.
- Given a wall between the crosshair and the target, then it is not targeted.
- Given the fire input (left mouse or right trigger) is pressed on a target, then the slot's `do_actions` run once, the target's health drops by the authored amount, a popup/spark/sound play, the slot's cooldown blocks a second activation inside `cooldown_secs`, and a target at 0 health goes down and respawns.
- Given `aim_target` is unset, then click and Tab targeting behave exactly as before.
- Given a first-person player switches camera mode away with `SetCameraMode`, then aim targeting and cursor capture stop and the cursor returns.

## Plan-review 2026-10-16 (system-architect + ux-gamedesigner-reviewer)

**Verdict: NEEDS MORE DESIGN WORK.** Facts verified by both reviewers: `Run` toggles, `Turn` comes from the right stick, no `CursorGrabMode` use, hit-scan via `PlayerTarget` + one Rapier ray is the right minimal footprint (no new `Action`, no `{self}`/`{target}` substitution work). Hit-scan resolved in `Update` is not replayable: log for future netcode. Plan 1 (`input_strafe_bindings.md`) must settle field representation (its decision 1) first.

### Blocking (resolve in this plan before coding)
1. **Layering mechanism (architect + UX).** "Authored > scheme > engine default" cannot be built with serde defaults: a `default = fn` cannot see `controls:`, and with IMPLICIT_SOME an authored `None` and an omitted field both parse as `None`. Under `controls: FirstPerson` a designer writing `strafe_left: None` would silently get the scheme's key back. **Recommended design:** a raw `InputMapDef` whose key fields record whether they were written (`#[serde(default, deserialize_with = ...)]` runs only when present, wrapping the inner `Option<String>`), `#[serde(deny_unknown_fields)]` on it, and `#[serde(from = "InputMapDef")]` on the resolved `InputMap`, which applies authored > scheme > engine default and keeps a per-field source for `inspect`. `InputMap::default()` must equal `InputMap::from(InputMapDef::default())` (single source). Runtime code, tests and the inspector keep one resolved type. Decide how `None` is written in RON (no `Some(...)`, `ron_lint`) and put the one-line doc rule in the plan: "Leave a field out to get the scheme's key; write `None` to unbind it; write a key name to replace it."
2. **Right-stick ownership (architect).** Stick X `Turn` comes from `input_translator_system` (`FixedUpdate`); the new stick yaw would live in `first_person_camera_system` (`Update`), so the `camera_modes` first-person room (`ThirdPerson` controls) would turn twice. Exactly one owner: a resolved `right_stick: Turn | Look` driven by `controls`; the camera system reads the stick only when `Look`. Also: `player_movement_system` is **not** untouched (`Run(held)`); in Hold mode `Run(_)` must not toggle.
3. **(v2) `aim_target_system` ordering (architect).** Correct set (`GameStreamSet::Targeting`, after `target_auto_clear_system`) but not enough: the camera chain is in no `GameplaySet`. Use `.before(first_person_camera_system)` (cycle-safe once the planned `CameraChainSet` lands after `Execute`), accepting one deterministic frame of latency; read moving targets with `fresh_global_transform`; tie-break by `SpawnId`, never `Entity` order; `run_if(sim_running)`; prefer an angular `radius_deg` over `radius_px` (a pixel radius covers different amounts on mobile vs 4K).

### Non-blocking, fold in before Ready
4. **`strafe_mouse_button` under `FirstPerson` = `None`** (Left is also the fire button); put it and the other scheme defaults in the "FirstPerson default" doc column. Keyboard look needs a named speed (reuse `gamepad_look_speed`, rename to `look_speed`, or a new field; `CameraConfig.look_speed` is Orbit-only).
5. **Duplicate-key and slot-key validate checks run on resolved bindings** (e.g. `controls: FirstPerson` + an old `left: "KeyA"` = A turns and strafes).
6. **Mouse button as slot field, not a `key` value (architect, precedent `gamepad_key`):** `parse_key` returns a `KeyCode` and is shared by `InputMap`, flycam, `global_key_bindings` and slots, so `"MouseLeft"` cannot go through it. Add a sibling `mouse_button: Option<String>` on `ActionSlotDef`; slot `key` identity, CLI `invalid_key` and cross-bar checks stay unchanged. Decide whether the click that **captures** the cursor also fires a shot (recommend: swallowed).

### Decisions made 2026-10-16 (after the architect re-reviewed the recommendations above; this section wins where it differs)
Frank delegated the calls to the author after the architect gave pros/cons; the five changes below supersede the earlier wording.
- **D1 layering: raw `InputMapDef` + `#[serde(from)]`, confirmed.** Written as a bare `None` (lint-clean; `ron_lint` only flags `Some(`). Works under `implicit_some` because a `deserialize_with` runs only when the field is present. Add a regression test pinning that `strafe_left: None` under `controls: FirstPerson` stays unbound.
- **D2 right-stick owner: CHANGED.** Decided from the **active camera**, not from `controls`: the translator skips stick X -> `Turn` for any player targeted by an active camera carrying `FirstPersonCameraMode` (it already is inserted/removed by `apply_camera_mode`, `entity_spawner.rs:1443/1479/1624`), and `first_person_camera_system` always owns stick look. **No `right_stick` field.** Reason: camera mode changes at runtime via `SetCameraMode`, which `validate` cannot see, so a scheme-based switch leaves a dead stick or a double turn after a switch.
- **D3 aim ordering: confirmed.** `.before(first_person_camera_system)` (cycle-safe, one deterministic frame of latency, and it reads the pose the player actually saw), `fresh_global_transform`, `SpawnId` tie-break, `run_if(sim_running)`, angular `radius_deg` (not raw pixels).
- **D4 mouse slot: confirmed, with a correction.** Sibling `mouse_button: Option<String>` on `ActionSlotDef`; `key` stays required and is the slot identity (events are `action_bar.*:{key}`); a fire slot is e.g. `key: "1", mouse_button: "Left"` (also a keyboard fallback). Mouse is shared hardware feeding the existing `direct_fired` flag (`action_bar.rs:~190`), and fires **only while the cursor is captured** (otherwise a click on an in-game panel also shoots).
- **D5 capture click and look gating: confirmed, with conditions.** The capturing click is swallowed (a "captured as of last frame" resource read by the action bar, capture applied after it). Gate **mouse look only**, and only when `capture_cursor: true`; stick and keyboard look never depend on capture.
- **D6 lost pointer lock: CHANGED.** No engine-owned `SimClock` hold (`Menu` is the only hold a designer can release; `FocusLoss` is reserved; a new hold could never be released by `ResumeGame`, leaving the game paused behind a working-looking menu, and it would add a `SimClock` writer outside the sanctioned set). Instead the capture system emits `GameEvent::Trigger("cursor.lock_lost")` in a `GameStreamSet` (covered by `schedule_order_tests`); the starter's `state_machine.ron` maps it to `PauseGame` + the pause menu; re-grab on Resume (a user gesture).
- **D7 missed shot: confirmed, with corrections.** The event is `action_bar.no_target:{key}` using the slot key (`action_bar.rs:268`), so `action_bar.no_target:1`, **not** `:MouseLeft` (fix Review item 9's example). The cooldown and cost checks run before the target check, so **a miss never starts the cooldown or spends cost**: acceptable for the starter, wrong for a real shooter; recorded as the reason for the v3 `fire` slot variant.
- **D8 own body: field confirmed, specified.** `FirstPersonCameraDef.hide_own_body: bool` implemented as `Visibility::Hidden` on the player root, inserted **in the spawn bundle** at the player-construction sites (no first-frame flash; `scene.ready` hiding always shows at least one frame), and handled by `apply_camera_mode` (un-hide when switching away, hide when switching in). Also suppresses the own nameplate (`should_insert_nameplate`) and world stat bar. Not `RenderLayers` (GLB descendants spawn async and non-zero layers lose layer-0 light shadows anyway). Limits: `SetEntityVisible` on the player overrides it (document "last writer wins"); split-screen first person needs per-camera layers (out of scope); confirm the camera is not a child of the player.
- **Biggest remaining risk (gates D4's capture gate, D5, D6): the engine may have no reliable view of the real pointer-lock state on the web.** The browser drops lock on Escape without telling the page or Bevy; Chrome refuses a re-lock for ~1 s after an exit and needs a recent user gesture; winit applies the grab outside the click handler and the request can be silently refused. **The v1 spike (Task 1) must prove a reliable lock-state signal before any of this is coded.** Fallback if Bevy/winit cannot provide one: `ironhold_web` listens for `pointerlockchange` and writes a core resource, a new runner -> core contract that needs Frank's explicit approval (core stays platform-agnostic).
