## What
A new example project, `first_person_starter`, that a designer copies as the starting point for a first-person shooter. The player is the male character (`character-male-01.glb`) seen through a `FirstPerson` camera with a centre crosshair, in a small test arena with shootable targets. Keyboard + mouse and a gamepad both work from the first frame, in the same session, with no mode switch. v1 is the movement/look feel; v2 adds aiming and firing so there is something to shoot at.

Nothing about the shooter is hardcoded in Rust: bindings, look speeds, aim range, damage, cooldown, sounds and effects are all RON. The engine only gains the generic mechanisms a first-person game needs and a third-person game does not.

## Why
`camera_modes` already has a `FirstPerson` room, but it is a camera smoke test (capsule, mouse look, WASD) and not a usable game starting point. Making it into one exposes real gaps, found by reading the code at `eb56cf3` (this is what the backlog item's open questions turned into):

| Question | Finding |
|---|---|
| Does first-person look work on a gamepad? | **Yaw only, indirectly.** `first_person_camera_system` (`capabilities/camera.rs:577-623`) reads `MouseMotion` only: it rotates the player `Transform` for yaw and keeps pitch on the camera mode state. The right stick X already feeds `InputAction::Turn` (`runtime/input.rs:375-377`), which rotates the character at `rot_speed` (`capabilities/player.rs:573-596`), an unrelated tank-turn rate. Right stick **Y has no first-person consumer** (only the Orbit system reads it, `camera.rs:270-276`). So there is no gamepad pitch. |
| Do A/D strafe? | **No by default.** A/D emit `Turn` unless `strafe_mouse_button` is held (`input.rs:335-364`). `InputMap.strafe_left/right` (Q/E) are defined but I found no reader of them in `src` (`grep strafe_left` hits only `schema/player.rs`). An FPS needs A/D to strafe and the mouse to turn. |
| Is sprint hold-to-run? | **No, a toggle.** Every `Run` press flips `is_running` (`player.rs:576-578`). FPS convention is hold. |
| Is there a projectile or hit-scan primitive? | **No.** No match for projectile/hitscan/raycast-fire in `crates/`. Rapier `cast_ray` is already used for NPC line of sight (`capabilities/npc.rs:139`), so the physics access pattern exists. |
| How does combat work today? | An action-bar slot's `do_actions` run against `{target}`, the player's `PlayerTarget` (e.g. `ModifyStat(key: "{target}.health", ...)`, `SpawnEffect`, `EmitEvent("entity.attacked:{target}")`, see `3rd_person_game_demo/scenes/main.scene.ron:437-446`). Cost, cooldown and `{target}` gating are device-agnostic. Target selection is screen-space proximity to the **mouse cursor** (`targeting.rs`), which an FPS does not have. |
| Can a slot be fired by a mouse button? | **No.** `ActionSlotDef.key` documents "Not supported: mouse buttons" (`schema/scene_v2.rs:1434`). `gamepad_key` already accepts `RightTrigger2` etc. (`schema/player.rs:573-576`). |
| Is the cursor captured? | **No.** Nothing in `crates/` references `CursorGrabMode`/`cursor_options`. In a browser, mouse look without pointer lock stops at the canvas edge, and the cursor stays visible. |
| Is there a crosshair? | No dedicated node. `UiNodeDef` has `Rect`, `Label`, `Group`, buttons, panels. A crosshair is authorable from `Rect`s in a centred `Group` (**verify** centring works as expected before relying on it). |
| Own body in view? | The camera sits at `eye_offset` inside the player. A GLB body would clip through the near plane and show the inside of the head. `Action::SetEntityVisible` exists, and Bevy visibility inherits to children, so hiding the player entity should hide the whole model (**verify**, including that the camera entity is not a child). It also drops the body's shadow, acceptable for v1. |
| Pause? | First-person mouse look already gates on `sim.is_running()` (`camera.rs:600-602`), so any new look input joins that gate. |

## Approach

The "Decisions made 2026-10-16" section at the end of this file records why each choice below was made; this section is the build spec and wins over the review history.

### v1: control scheme, look, cursor capture, project

**Prerequisite (merged 2026-10-16, `done/input_strafe_bindings.md`):** `InputMap` key fields are `Option<String>` (`None` = unbound), `strafe_left/right` are real and default to `None`, and `ironhold validate` already reports unknown/empty/duplicate keys and key-vs-slot collisions. `InputMap` is the **resolved** type everything reads.

1. **Control schemes with per-binding override.** Frank's principle: the game creator can always override any binding. Resolution order per field: **written by the designer, then the scheme's default, then the engine default.**
   - New `InputMap.controls: ThirdPerson | FirstPerson` (unquoted enum, `velocity_curve: EaseOut` style; not named `preset`, which `camera_modes` uses for scene registry entries). `ThirdPerson` is the default and reproduces today's behaviour exactly. `FirstPerson` defaults: `left`/`right` (turn) unbound, `strafe_left: "KeyA"`, `strafe_right: "KeyD"`, `strafe_mouse_button: None` (left mouse is the fire button), `run_mode: Hold`. `SideScroll` is **not** in the enum: it needs different movement (fixed world axis, locked depth), not just different keys.
   - **Mechanism:** a raw `InputMapDef` whose key fields record whether they were written (`#[serde(default, deserialize_with = ...)]` runs only when the field is present, wrapping the inner `Option<String>`; works under `implicit_some`), `#[serde(deny_unknown_fields)]`, and `#[serde(from = "InputMapDef")]` on the resolved `InputMap`, which applies the three-step order and keeps a per-field source (`authored` / `scheme:FirstPerson` / `default`). `InputMap::default()` must equal `InputMap::from(InputMapDef::default())` (one source). A bare `None` is how a designer unbinds (lint-clean, `ron_lint` only flags `Some(`). Doc rule, one sentence: "Leave a field out to get the scheme's key; write `None` to unbind it; write a key name to replace it."
   - **Layer split:** what keys and sticks do (turn vs strafe, sprint mode) belongs to `InputMap`/`controls:`; how look feels (`look_speed`, `invert_y`, `capture_cursor`, `hide_own_body`) belongs to `FirstPersonCameraDef`. `controls:` never sets camera fields.
   - Authored example: `inputs: ( controls: FirstPerson, gamepad_index: 0, run_mode: Toggle )` (doc override example: `run_mode`, not an unbinding).
   - **Validate/CLI:** warn when `controls:` does not match the player's camera mode (`FirstPerson` with an `Orbit` camera, `ThirdPerson` with a `FirstPerson` camera; runtime `SetCameraMode` switches are invisible to `validate`, document that); the existing duplicate-key and key-vs-slot checks run on the **resolved** bindings (they already deserialize through `InputMap`); `ironhold inspect`/`query` prints each effective binding with its source.
2. **Right-stick ownership: decided from the active camera.** The translator (`input_translator_system`) skips right-stick-X -> `Turn` for any player targeted by an active camera carrying `FirstPersonCameraMode` (found by scanning the camera query each tick; `apply_camera_mode` already inserts/removes that component, `entity_spawner.rs`), and `first_person_camera_system` always owns stick look. No `right_stick` field. This is correct under runtime `SetCameraMode` switches, which a scheme-based switch is not. No shipped `FirstPerson` player has a `gamepad_index`, so existing projects are unaffected.
3. **Look in `first_person_camera_system`.** Add right stick X (yaw) and Y (pitch) via the owning player's `Option<&BoundGamepad>` resolved through `CameraTargets` (never a required `&BoundGamepad`, `capabilities/CLAUDE.md`), and keyboard look through the existing `InputMap.look_left/right/up/down` fields (Orbit-only today). New `FirstPersonCameraDef` fields: `look_speed: f32` (rad/s, default `2.5`, used for **stick and keyboard** look, not mouse), `invert_y: bool` (default `false`, applies to mouse, stick and keyboard). Stick/keyboard look is dt-scaled on the sim clock and sits behind the existing `sim.is_running()` gate; yaw is written to the player `Transform` exactly like the mouse path, so inputs compose. Pitch sign is pinned by a regression test, not asserted from hardware feel.
4. **`InputMap.run_mode: Toggle | Hold`** (default from the scheme: `Toggle` / `Hold`; overridable). `Hold` emits `InputAction::Run(held)` every tick and `player_movement_system` sets `is_running = held`; in Hold mode a `Run(_)` must never toggle. The toggle path is unchanged. (`player_movement_system` is therefore touched, minimally.)
5. **Cursor capture: `FirstPersonCameraDef.capture_cursor: bool`** (default `false`, so the existing `camera_modes` room is unchanged). When true: grab and hide the cursor on the first canvas click (browsers need a user gesture for pointer lock); that capturing click is **swallowed** (it does not fire a shot: the action bar reads a "captured as of last frame" resource, capture is applied after the action bar runs); mouse look is gated on being captured (stick and keyboard look never depend on capture); the cursor is released while a `SimClock` hold is active (pause menu) so UI is clickable, re-grabbed on the next click after resume, and released on `SetCameraMode` away from first person or `LoadScene` into a scene without it. **Lost pointer lock** (browser Escape, which the page may never see as a keydown): the capture system emits `GameEvent::Trigger("cursor.lock_lost")` in a `GameStreamSet` (covered by `schedule_order_tests`); the starter's `state_machine.ron` maps it to `PauseGame` + the pause menu (an engine-owned `SimClock` hold is rejected: `ResumeGame` only releases the `Menu` hold, so a new hold could never be released by the designer). Native and WASM both go through Bevy's `CursorOptions` in `ironhold_core` (platform-agnostic); `cfg` only where Bevy/winit require it (winit `Locked` is unsupported on Windows/X11, `Confined` on macOS: fall back, `framepace` is the precedent). Cosmetic window state, never pushes to `ActionQueue`.
   - **Spike first (Task 1, gates this whole item):** prove a **reliable lock-state signal** on WebGPU in Chrome/Edge. The browser drops lock on Escape without telling the page or Bevy, Chrome refuses a re-lock for about 1 s after an exit and needs a recent user gesture, and winit applies the grab outside the click handler so a request can be silently refused. Also check whether a locked cursor still hits UI buttons under the centre. If Bevy/winit cannot provide the signal, the fallback is `ironhold_web` listening for `pointerlockchange` and writing a core resource: a new runner -> core contract that needs **Frank's explicit approval** (core stays platform-agnostic). If capture cannot be made reliable, v1 ships mouse look without `capture_cursor` and documents the edge-of-canvas limitation.
6. **`FirstPersonCameraDef.hide_own_body: bool`** (default `false`). Implemented as `Visibility::Hidden` on the player root, inserted **in the spawn bundle** at the player-construction sites (no first-frame flash: hiding on `scene.ready` always shows at least one frame of the inside of the head) and handled by `apply_camera_mode` (un-hide when switching away, hide when switching in). Also suppresses the own nameplate (`should_insert_nameplate`) and world stat bar. Not `RenderLayers` (GLB descendants spawn asynchronously and non-zero layers lose layer-0 light shadows anyway). Limits to document: `SetEntityVisible` on the player overrides it (last writer wins); the body casts no shadow; split-screen first person needs per-camera layers (out of scope). Verify the camera is not a child of the player.
7. **Project `first_person_starter`** (`/new-project first_person_starter`, never hand-copied). Scene `main` (arena). The project's own `assets.ron` entries for `character_male` (`shared/models/characters/character-male-01.glb#Scene0`) plus the `animation_sources` `3rd_person_game_demo`'s player uses, and `overrides/model_fixes.ron` if the male model needs the same fix. Prefab `player_male_fps`: `camera_mode: FirstPerson((eye_offset: (0.0, 1.65, 0.0), fov: 90.0, capture_cursor: true, hide_own_body: true, ...))` and `inputs: (controls: FirstPerson, gamepad_index: 0)`; every first-person field commented. `gamepad_index` must be set for a single-player gamepad to work at all, so its doc row's "Local co-op only" label is corrected. Project file: `global_claimed_gamepad_bindings: { "Start": "toggle_pause" }` for gamepad pause. `state_machine.ron`: `cursor.lock_lost` -> `PauseGame` + pause menu, `resume` -> `UnloadOverlay` + `ResumeGame`. Crosshair: a centred `Group` of small `Rect`s (verify centring in the spike). Arena from primitives: floor, perimeter walls, cover boxes, a ramp or steps (jump and slope handling), `training_dummy` props at several ranges (static in v1). Hints: one `Label` per device (budget about 45 characters per line at 22px, ASCII only, no em dash), accurate for both.
8. **Bindings table** (scene hint and README row):

| Action | Keyboard + mouse | Gamepad |
|---|---|---|
| Move | WASD (A/D strafe) | Left stick |
| Look | Mouse (keyboard look keys as a fallback) | Right stick (X yaw, Y pitch) |
| Jump | Space | South (A) |
| Sprint (hold) | Shift | East (B) |
| Fire (v2) | Left mouse | Right trigger (`RightTrigger2`) |
| Aim down sights (later) | Right mouse | Left trigger |
| Pause | Escape (releases the cursor) / P | Start |

### v2: aim targeting and fire

The combat pipeline already exists (`{target}`, slot cost/cooldown, `ModifyStat`, `ShowDamagePopup`, `SpawnEffect`). What is missing is **who the target is when there is no cursor**, and a fire input that is not a keyboard key. v2 adds two small generic mechanisms and **no weapon system**:

1. **`FirstPersonCameraDef.aim_target: Option<AimTargetDef>`** with `range` (default `40.0`), `radius_deg` (default `3.0`, an **angular** catch circle so it covers the same view fraction on mobile and 4K) and `require_line_of_sight` (default `true`). When set, a new `aim_target_system` drives that player's `PlayerTarget` each frame from the **viewport centre**: among `targetable` entities within `range` and `radius_deg`, pick the one nearest the centre (screen-space projection and `select_aim_height` as in `click_select_system`, moving targets read with `fresh_global_transform`, ties broken by `SpawnId`, never `Entity` order), then, if `require_line_of_sight`, cast **one** Rapier ray from the camera to it (`exclude_sensors()`, ignore the player's own collider) and drop the target if something else is hit first. Everything downstream (`{target}`, `target.changed`, HUD variables, indicator ring) is unchanged, so a shot slot is today's slot RON. `click_select_system` and `tab_targeting_system` skip a player whose camera has `aim_target`. **Ordering:** `GameStreamSet::Targeting`, after `tab_targeting_system` and `target_auto_clear_system`, before `GameStreamSet::ActionBar` (`capabilities/CLAUDE.md`), `run_if(sim_running)`, and `.before(first_person_camera_system)` (cycle-safe even once the planned `CameraChainSet` lands after `Execute`; one frame of deterministic latency, and it reads the pose the player actually saw). Extend `tests/schedule_order_tests.rs`.
2. **Mouse button on action-bar slots: a sibling field `mouse_button: Option<String>`** on `ActionSlotDef` (`"Left"`, `"Right"`, `"Middle"`), mirroring `gamepad_key`. `key` stays required and is the slot identity (events are `action_bar.*:{key}`); a fire slot is e.g. `key: "1", mouse_button: "Left", gamepad_key: "RightTrigger2"` (the key is also a keyboard fallback). The mouse is shared hardware feeding the existing `direct_fired` flag (`action_bar.rs` ~190) and fires **only while the cursor is captured** (otherwise a click on an in-game panel also shoots). Semi-auto: one shot per press, bounded by `cooldown_secs`; hold-to-repeat is deferred. Validate: warn when a mouse-button slot shares a button with `orbit_button`, `strafe_mouse_button` or click-select; reject near-miss names (`"LeftMouse"`, `"Mouse1"`).
3. **Shot RON** in the scene's action bar (verify an `ActionBar` can be non-visual, else give it a small ammo-style HUD strip): `PlaySound(key: "shot")`, `ModifyStat(key: "{target}.health", delta: -25.0)`, `ShowDamagePopup`, `SpawnEffect(key: "hit_spark", entity: "{target}")`, `EmitEvent("entity.attacked:{target}")`. **A miss** is handled in pure RON by the existing `action_bar.no_target:{key}` event (`action_bar.rs` ~268, keyed by the slot key, so `action_bar.no_target:1`): `on: "action_bar.no_target:1"` -> `PlaySound(...)`. The cooldown and cost checks run before the target check, so **a miss never starts the cooldown or spends cost**: acceptable for the starter, wrong for a real shooter, and the reason for the later `fire` slot variant.
4. **Training dummies:** prefab with `targetable: true`, an entity-scoped `{self}.health` stat, and a behavior file that goes to a "down" state at 0 health and respawns via `SetDespawnTimer`/spawn (not `EmitEventAfterDelay` + `Despawn`, whose stale timers survive `LoadScene` and can hit a reused id). Model the wiring on `enemy_zombie.behavior.ron` after reading it. Log (in the plan history) that hit-scan resolved in `Update` is not replayable, for future netcode.

## Spike A result: cursor capture (source reading, 2026-10-17; browser confirmation still to do)

Read from `bevy_window 0.18.0`, `bevy_winit 0.18.0` and `winit 0.30.12` in the cargo registry. **Conclusion: the engine has no way to see the real pointer-lock state on the web, so the runner -> core fallback is required, not optional.**
- Bevy 0.18 exposes the grab as the `CursorOptions` **component** on the window (`grab_mode`, `visible`). `bevy_winit`'s apply system runs only on `Changed<CursorOptions>` (`bevy_winit/src/system.rs` ~575-600), tries `Confined` then falls back to `Locked` (and the reverse) in `attempt_grab` (`winit_windows.rs` ~415-440), and its own comment says the grab "can change through external means, leaving the cache outdated".
- On the web, `winit` implements `set_cursor_grab` as `canvas.request_pointer_lock()` / `document.exit_pointer_lock()` and **always returns `Ok`** (`web/web_sys/canvas.rs` ~175-181, `web/window.rs` ~230-240); `Confined` is `NotSupported` (so Bevy's fallback to `Locked` is what runs). There is **no `pointerlockchange` / `pointerlockerror` listener anywhere in winit's web backend** (grep over `platform_impl/web` finds only the two calls above). So: a request made while the browser refuses it (no recent user activation, or Chrome's re-lock delay after an Escape exit) fails silently; the user pressing Escape releases the lock with nothing reaching Bevy; and `CursorOptions.grab_mode` stays `Locked` while the real state is unlocked. Re-grabbing after an external release needs a **forced** `Changed<CursorOptions>` (write `None`, then `Locked`).
- `ironhold_web` today only reads URL params through `web-sys` (`Window`, `Location`, `UrlSearchParams`; `crates/ironhold_web/src/lib.rs`). It has no event listeners.
- Native (Windows/macOS/Linux): grab is synchronous through winit and Escape is not special, so the engine's own `CursorOptions` is a reliable state there.

**Design that follows (needs Frank's approval, a new runner -> core contract):**
1. `ironhold_core` defines a platform-agnostic resource `CursorLockState { locked: bool, source_reliable: bool }` (no `web-sys`, no `cfg(wasm32)` in core).
2. `ironhold_web` (the thin runner) registers `document` `pointerlockchange` and `pointerlockerror` listeners and writes the resource from `document.pointerLockElement == canvas`; adds the `Document`, `Element`, `Event` web-sys features it needs.
3. Native: the core capture system sets `locked` itself right after it writes `CursorOptions` (synchronous, reliable).
4. The capture system emits `cursor.lock_lost` (locked -> not locked without the engine having asked), applies mouse-look gating and the swallowed capture click from `CursorLockState`, never from `CursorOptions`, and forces a `Changed<CursorOptions>` to re-grab.
Browser confirmation (Chrome/Edge WebGPU) of the user-gesture timing (the request is issued from a Bevy system on the frame after the click, inside Chrome's transient-activation window) and of the ~1 s re-lock delay happens in the first slice of code, behind this contract.

## Out of scope (logged as follow-ups when v2 lands, not part of this plan)
Ammo and reload, hold-to-repeat fire, recoil and spread, weapon view-model (hands/gun mesh attached to the camera), aim-down-sights zoom (a `fov` change via `SetCameraMode` preset), hit-marker and damage-direction HUD, enemy AI that shoots back, shadow-only own body, pick-ups, multiple weapons and weapon switching, **local co-op / split-screen first person** (one shared mouse cannot drive two first-person cameras, same limit as Orbit's `orbit_button: "None"` rule), input remapping UI (already queued separately), `Fixed`-tick sim for the shot (aim runs in `Update` like targeting, deliberately).

## Risks
- **Pointer lock on the web** is the main unknown (lock-state signal, Escape, Chrome's re-lock delay, winit applying the grab outside the click handler). It cannot be exercised by the headless suite; the playtest is manual (`python serve.py` in the worktree), and Playwright `--real-gpu` only covers the static baseline. Port rule: use a different port for `test_web.py` than a manual `serve.py`. Gated by Spike A; the runner -> core fallback needs Frank's approval.
- **One yaw writer.** `first_person_camera_system` writes the player's `Transform` rotation from per-frame input while physics runs in `FixedUpdate`; stick/keyboard/mouse all go through that one writer, and the translator must not also emit `Turn` for these players (right-stick ownership, item 2).
- **Hidden body = no body shadow, no own nameplate/stat bar.** Documented limit.
- **Aim system cost:** one projection pass over `targetable` entities and at most one ray per frame per aiming player, only when `aim_target` is set; `wasm-perf-reviewer` should confirm.
- **Gamepad quirks** already logged (`Web gamepad robustness`, stick drift/deadzone) apply; v1 reuses `InputMap.gamepad_deadzone`.
- **Resolution layer is new surface** (`InputMapDef` + `serde(from)`): the regression test for authored `None` under a scheme is the guard; `InputMap::default()` must stay equal to the resolved empty block.

## Acceptance criteria
v1
- Given `first_person_starter` with keyboard and mouse, when the player uses WASD, the mouse and Space/Shift, then they strafe (A/D never turn the character), look in yaw and pitch (pitch clamped), jump, and sprint only while Shift is held.
- Given a gamepad, when the left stick moves and the right stick looks, then movement and yaw/pitch look work with no keyboard or mouse input, drift below the deadzone does nothing, and pushing the stick up looks up (inversion only with `invert_y`).
- Given both devices in one session, then neither blocks the other and the on-screen hints are accurate for both.
- Given the simulation is paused or the window loses focus, then look input does not rotate the player and the cursor is released and visible; on resume and a click, capture resumes.
- Given the browser releases pointer lock (Escape), then `cursor.lock_lost` fires, the game pauses with the menu shown, and resuming (a click) re-captures.
- Given `camera_modes` and `3rd_person_game_demo`, then play is unchanged (existing suites pass unchanged; Q and E still do nothing; a `FirstPerson` player in `camera_modes` still turns on A/D).
- Given a project with `controls: FirstPerson` on an Orbit-camera player (or `ThirdPerson` on a FirstPerson-camera player), then `ironhold validate` warns; and `ironhold inspect`/`query` lists each effective binding with its source (`authored`, `scheme:FirstPerson`, `default`).
- Given `strafe_left: None` under `controls: FirstPerson`, then the key stays unbound.
- Given the male model, then the player's own body is not visible and nothing clips through the near plane.

v2
- Given the crosshair is over a `targetable` target in range and unobstructed, then that target is the player's `PlayerTarget`, `{target}` resolves to it, and the target HUD variable names it.
- Given a wall between the crosshair and the target, then it is not targeted.
- Given the fire input (left mouse while captured, or right trigger) is pressed on a target, then the slot's `do_actions` run once, the target's health drops by the authored amount, a popup/spark/sound play, the cooldown blocks a second activation inside `cooldown_secs`, and a target at 0 health goes down and respawns.
- Given a fire press with no target, then `action_bar.no_target:{key}` fires and the starter's RON plays a miss sound.
- Given a click on an in-game panel while the cursor is released, then no shot fires; the capturing click does not fire a shot.
- Given `aim_target` is unset, then click and Tab targeting behave exactly as before.
- Given a first-person player switches camera mode away with `SetCameraMode`, then aim targeting and cursor capture stop and the cursor returns.

### Decisions made 2026-10-16 (after the architect re-reviewed the recommendations above; this section wins where it differs)
Frank delegated the calls to the author after the architect gave pros/cons; the five changes below supersede the earlier wording.
- **D1 layering: raw `InputMapDef` + `#[serde(from)]`, confirmed.** Written as a bare `None` (lint-clean; `ron_lint` only flags `Some(`). Works under `implicit_some` because a `deserialize_with` runs only when the field is present. Add a regression test pinning that `strafe_left: None` under `controls: FirstPerson` stays unbound.
- **D2 right-stick owner: CHANGED.** Decided from the **active camera**, not from `controls`: the translator skips stick X -> `Turn` for any player targeted by an active camera carrying `FirstPersonCameraMode` (it already is inserted/removed by `apply_camera_mode`, `entity_spawner.rs:1443/1479/1624`), and `first_person_camera_system` always owns stick look. **No `right_stick` field.** Reason: camera mode changes at runtime via `SetCameraMode`, which `validate` cannot see, so a scheme-based switch leaves a dead stick or a double turn after a switch.
- **D3 aim ordering: confirmed.** `.before(first_person_camera_system)` (cycle-safe, one deterministic frame of latency, and it reads the pose the player actually saw), `fresh_global_transform`, `SpawnId` tie-break, `run_if(sim_running)`, angular `radius_deg` (not raw pixels).
- **D4 mouse slot: confirmed, with a correction.** Sibling `mouse_button: Option<String>` on `ActionSlotDef`; `key` stays required and is the slot identity (events are `action_bar.*:{key}`); a fire slot is e.g. `key: "1", mouse_button: "Left"` (also a keyboard fallback). Mouse is shared hardware feeding the existing `direct_fired` flag (`action_bar.rs:~190`), and fires **only while the cursor is captured** (otherwise a click on an in-game panel also shoots).
- **D5 capture click and look gating: confirmed, with conditions.** The capturing click is swallowed (a "captured as of last frame" resource read by the action bar, capture applied after it). Gate **mouse look only**, and only when `capture_cursor: true`; stick and keyboard look never depend on capture.
- **D6 lost pointer lock: CHANGED.** No engine-owned `SimClock` hold (`Menu` is the only hold a designer can release; `FocusLoss` is reserved; a new hold could never be released by `ResumeGame`, leaving the game paused behind a working-looking menu, and it would add a `SimClock` writer outside the sanctioned set). Instead the capture system emits `GameEvent::Trigger("cursor.lock_lost")` in a `GameStreamSet` (covered by `schedule_order_tests`); the starter's `state_machine.ron` maps it to `PauseGame` + the pause menu; re-grab on Resume (a user gesture).
- **D7 missed shot: confirmed, with corrections.** The event is `action_bar.no_target:{key}` using the slot key (`action_bar.rs:268`), so `action_bar.no_target:1`, **not** `:MouseLeft` (fix Review item 9's example). The cooldown and cost checks run before the target check, so **a miss never starts the cooldown or spends cost**: acceptable for the starter, wrong for a real shooter; recorded as the reason for the v3 `fire` slot variant.
- **D8 own body: field confirmed, specified.** `FirstPersonCameraDef.hide_own_body: bool` implemented as `Visibility::Hidden` on the player root, inserted **in the spawn bundle** at the player-construction sites (no first-frame flash; `scene.ready` hiding always shows at least one frame), and handled by `apply_camera_mode` (un-hide when switching away, hide when switching in). Also suppresses the own nameplate (`should_insert_nameplate`) and world stat bar. Not `RenderLayers` (GLB descendants spawn async and non-zero layers lose layer-0 light shadows anyway). Limits: `SetEntityVisible` on the player overrides it (document "last writer wins"); split-screen first person needs per-camera layers (out of scope); confirm the camera is not a child of the player.
- **Biggest remaining risk (gates D4's capture gate, D5, D6): the engine may have no reliable view of the real pointer-lock state on the web.** The browser drops lock on Escape without telling the page or Bevy; Chrome refuses a re-lock for ~1 s after an exit and needs a recent user gesture; winit applies the grab outside the click handler and the request can be silently refused. **The v1 spike (Task 1) must prove a reliable lock-state signal before any of this is coded.** Fallback if Bevy/winit cannot provide one: `ironhold_web` listens for `pointerlockchange` and writes a core resource, a new runner -> core contract that needs Frank's explicit approval (core stays platform-agnostic).
