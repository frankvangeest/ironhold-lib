# Feature: `backend/` folder - a local Nakama for development

_Status: Draft (decisions answered 2026-11-05, plan-review pending)_
_Planned at: `dd2d811` (2026-11-05)_

## What

One folder, `backend/`, at the repo root holds everything needed to run a Nakama on the developer's machine and to hand a server admin the
files the engine needs on a server: a local dev stack (`docker-compose.yml`, `up.sh`, `down.sh`, a README) plus the documented workflow for
generating the server module and game list with `ironhold backend config`. A designer or engine developer can run
`backend/up.sh` and have a local server that the contract test and the native runner can talk to, without touching the homelab.

## Why

- **Prerequisite of backend v3a** (`planning/features/backend_abstraction.md`, backlog "Backend v3a"): v3 is all server-module work and must
  not be tested against the live demo data on the homelab.
- Today the local Nakama exists only as a test fixture (`crates/ironhold_nakama/tests/contract/`), torn down after every run, so there is
  nothing to leave running while building a lobby screen.
- The Nakama version is pinned in separate places (the contract compose, the homelab compose). The engine side should pin it once.

## Findings (read from the repo, 2026-11-05)

1. **Docker is installed but its daemon is not running on this machine** (`docker 29.9.2`, `compose v5.6.1`; the engine pipe
   `dockerDesktopLinuxEngine` does not exist). Docker Desktop has to be started by Frank before any container work; nothing here may start it
   for him.
2. **The module is already shipped as data, and the CLI already produces the deployable files.** `crates/ironhold_nakama/src/server_config.rs:11`
   embeds `server/ironhold.lua` with `include_str!`, and `ironhold backend config <project>... --out <dir>` (`crates/ironhold_cli/src/commands/backend.rs`)
   writes both `ironhold.lua` and the generated `ironhold_games.lua`. So the artifact a server needs is the CLI's output, not a path in the
   source tree. A unit test (`server_config.rs:130`) also embeds the contract fixture `tests/contract/modules/ironhold_games.lua`.
3. The contract compose (`crates/ironhold_nakama/tests/contract/docker-compose.yml`) pins `registry.heroiclabs.com/heroiclabs/nakama:3.41.0` and
   `postgres:16-alpine`; the homelab pins `heroiclabs/nakama:3.41.0` and `postgres:16.15-alpine`. Same Nakama version, different image paths.
4. The web build cannot pick a server from the page address (a link must never choose which server receives a device id); a real endpoint comes
   from `backend.ron`. Native accepts `--backend <endpoint>`.

## Approach

```
backend/
  README.md            what this is, the warning (default keys, localhost only, never deployable), how to run a game against it
  .env                 NAKAMA_IMAGE / POSTGRES_IMAGE pins, committed: the one place the engine side pins versions
  docker-compose.yml   nakama + postgres, ports bound to 127.0.0.1 only, Nakama's default keys, modules mounted from ./modules
  up.sh / down.sh      up.sh [project...]: generate ./modules with the cached CLI, start the stack, wait for the healthcheck, print the endpoint,
                       the default server key and how to run a game; down.sh [-v] stops it (-v drops the database volume)
  modules/             generated by up.sh, gitignored
```

- **Module source stays in `crates/ironhold_nakama/server/ironhold.lua`** (Open question 1, recommended). Moving it to `backend/` would force
  `include_str!("../../../backend/...")` out of the crate, split the CLI's embedded copy from its source folder, and add churn for no gain, because
  the homelab deploy fetches the **CLI output**, not a source path. `backend/` generates `modules/` from it on every `up.sh`, so a local run
  always tests the current module.
- `up.sh` uses the cached `tools/bin/ironhold` (see root `CLAUDE.md`, "Caching the ironhold_cli binary") and falls back with a clear message if it is
  missing or stale. Default projects: every project under `assets/projects/` that has a `backend.ron` with a non-`fake://` endpoint, so a new
  game appears without editing the script; `up.sh <project>...` overrides.
- **Contract test reuse.** `tests/contract/run.sh` stops carrying its own compose: it uses `backend/docker-compose.yml` plus a small override
  file (fixture `modules/`, the 7200 s token expiry, project name so it never collides with a dev stack that is running). Both read the pins
  from `backend/.env`, so the Nakama version is pinned once in the engine repo.
- **Safety:** ports bound to `127.0.0.1`; default `defaultkey` and console credentials; the README and the compose file's first lines say it is
  never a deployable config. No secrets in the folder. Production and staging compose, vault secrets, Traefik and Cloudflare stay in the
  homelab repo; the homelab deploy script takes `ironhold backend config` output (decided in the homelab staging item, "module and config
  deploy path").
- **Out of scope:** a dev stack for a web build (see Open question 2), any CI, any Windows `.ps1` twin (the repo's shell rule is Bash).

## Decisions (answered by Frank, 2026-11-05)

1. **Module location:** `ironhold.lua` stays in `crates/ironhold_nakama/server/`; `backend/` generates `modules/` from the CLI. (The backlog
   item's "moved from" wording is superseded.)
2. **Local server for a web playtest:** a local variant of `backend_demo_lobby` with `endpoint: "http://127.0.0.1:7350"`, decided when that project
   is planned; this folder only makes the server reachable.
3. **Docker Desktop:** `up.sh` does not start it; it prints "start Docker Desktop" and exits non-zero (proposed, not objected to).

## Acceptance criteria

- Given Docker is running, when a developer runs `backend/up.sh`, then Nakama and Postgres reach healthy, `ironhold.lua` and `ironhold_games.lua`
  for the chosen projects are in `backend/modules/`, and the script prints `http://127.0.0.1:7350` and the default server key.
- Given the stack is up, when `tests/contract/run.sh` runs, then it uses the pins in `backend/.env` and passes, and a running dev stack is not disturbed.
- Given no Docker daemon, when `up.sh` runs, then it exits non-zero with a message that names Docker Desktop, and nothing else is changed.
- The Nakama image tag appears in exactly one file in this repo (`backend/.env`).
