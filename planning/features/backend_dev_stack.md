# Feature: `backend/` folder - a local Nakama for development

_Status: Ready (plan-review 2026-11-05: both reviews returned "needs more design work", every finding folded in below, no open design choice left)_
_Planned at: `dd2d811` (2026-11-05)_

## What

One folder, `backend/`, at the repo root holds everything an **engine developer** needs to run a Nakama on their own machine: a local dev
stack (`docker-compose.yml`, `.env`, `up.sh`, `down.sh`, a README) that generates the server module and game list with
`ironhold backend config` and starts Nakama + Postgres bound to localhost. It needs a repo clone, Rust (for the cached CLI and the native
runner), Docker and Git Bash on Windows. It is not a designer path: the hosted web build cannot use a local server (docs say so).

## Why

- **Prerequisite of backend v3a** (`planning/features/backend_abstraction.md`, backlog "Backend v3a"): v3 is all server-module work and must
  not be tested against the live demo data on the homelab.
- Today the local Nakama exists only as a test fixture (`crates/ironhold_nakama/tests/contract/`), torn down after every run, so there is
  nothing to leave running while building a lobby screen.
- The engine side should pin the Nakama and Postgres versions once.

## Findings (read from the repo, 2026-11-05)

1. **Docker is installed but its daemon is not running on this machine** (`docker 29.9.2`, `compose v5.6.1`). Frank starts Docker Desktop; nothing
   here starts it for him.
2. **The module is shipped as data and the CLI produces the deployable files.** `crates/ironhold_nakama/src/server_config.rs:11` embeds
   `server/ironhold.lua` with `include_str!`; `ironhold backend config <project>... --out <dir>` writes `ironhold.lua` and the generated
   `ironhold_games.lua`. A unit test (`server_config.rs:130`) also embeds `tests/contract/modules/ironhold_games.lua`, so **that fixture file stays where it is**.
3. The contract compose pins `registry.heroiclabs.com/heroiclabs/nakama:3.41.0` and `postgres:16-alpine`; the homelab pins `heroiclabs/nakama:3.41.0`
   and `postgres:16.15-alpine`.
4. The web build cannot pick a server from the page address; a real endpoint comes from `backend.ron`. Native `--backend <endpoint>` accepts any
   endpoint but **never sends `backend.ron`'s `server_key`** (`crates/ironhold_native/src/nakama.rs:48`): the key comes from `NAKAMA_SERVER_KEY`.
5. `tools/bin/ironhold` embeds `ironhold.lua` at build time, so a stale cached CLI generates a stale module.
6. The repo has no `.gitattributes`, `core.autocrlf=true`, and `run.sh` is already CRLF in the working tree; a `\r` in a shell script or an image tag breaks both.

## Decisions (answered by Frank, 2026-11-05)

1. **Module location:** `ironhold.lua` stays in `crates/ironhold_nakama/server/`; `backend/` generates `modules/` from the CLI. (The backlog item's "moved from" is superseded.)
2. **Local server for a web playtest:** a local variant of `backend_demo_lobby` with `endpoint: "http://127.0.0.1:7350"`, decided when that project is planned; this folder only makes the server reachable.
3. **Docker Desktop:** `up.sh` does not start it; it exits non-zero with a message.

## Approach

```
backend/
  README.md            prerequisites first (repo clone, Rust, Docker Desktop, Git Bash), the warning, the run command, troubleshooting
  .env                 pins only, never secrets: NAKAMA_IMAGE=heroiclabs/nakama:3.41.0, POSTGRES_IMAGE=postgres:16.15-alpine
  docker-compose.yml   `name: ironhold-dev`; nakama + postgres; 7350 and 7351 bound to 127.0.0.1 (gRPC 7349 not published); healthcheck
  up.sh / down.sh      see below
  modules/             generated by up.sh, gitignored
```

**Compose (one file, no override file).** Everything a second caller needs to change is a variable with a default, so there is nothing to layer and no entrypoint copy that can drift:
`name: ironhold-dev`; `image: ${NAKAMA_IMAGE}` / `${POSTGRES_IMAGE}`; ports `127.0.0.1:${NAKAMA_PORT:-7350}:7350` and `127.0.0.1:${NAKAMA_CONSOLE_PORT:-7351}:7351`;
volume `${NAKAMA_MODULES:-./modules}:/nakama/data/modules`; `--session.token_expiry_sec ${NAKAMA_TOKEN_EXPIRY:-7200}` in the single entrypoint;
vendor healthcheck (`/nakama/nakama healthcheck`, as in the homelab compose) so `docker compose up -d --wait` works. The Postgres password is a
literal in the compose file (a throwaway local database), not in `.env`, so `.env` never looks like a secrets file. The compose file starts
with a warning header: local only, default keys, never a deployable config.

**`up.sh [project...]`** (all calls pass `--env-file "$repo/backend/.env"` and run from the repo root, so nothing depends on the working directory):
1. Check `docker` exists and `docker info` answers **before generating or writing anything**; otherwise exit non-zero with one of: "Docker is not installed",
   "Start Docker Desktop and run again". Check that port 7350 is free ("something is already listening on 7350; run backend/down.sh or stop it").
2. Check the CLI: `tools/bin/ironhold(.exe)` must exist and be newer than `crates/ironhold_nakama/src`, `crates/ironhold_nakama/server` and
   `crates/ironhold_core/src/schema`; if not, print the two rebuild lines from root `CLAUDE.md` and exit non-zero.
3. Generate `backend/modules/`: `tools/bin/ironhold backend config <projects> --out backend/modules`, then **copy
   `crates/ironhold_nakama/server/ironhold.lua` over `backend/modules/ironhold.lua`** (the cached CLI's embedded copy can be stale; the source file is what a local run must test).
   **Default projects:** every project under `assets/projects/` that has a `backend_path` (the CLI validates them; a `fake://` project is included because
   the game must be known to the server to sign in). Explicit arguments override. The CLI rejects duplicate `game_id`s; the README documents that
   (a future local variant of a demo must use a different project folder and `game_id`, or be named explicitly instead of the default).
4. `docker compose ... up -d --wait` (first run downloads the images, about 200 MB: say so before it starts; time out with a clear message, not a hang).
   **Re-run semantics:** if the stack is already up, `up.sh` regenerates `modules/` and restarts the `nakama` container only (Nakama cannot hot-reload
   modules), so adding a leaderboard or a game is one command; it never touches the database volume.
5. Print, in one block, with the warning on the line above it: `LOCAL ONLY - default keys - never deploy this`, then a complete command that signs in when run
   literally, naming a project that was included: `NAKAMA_SERVER_KEY=defaultkey cargo run -p ironhold_native -- --project <included> --backend http://127.0.0.1:7350`
   (checked against the native runner's real flags when the script is written), the endpoint, the console URL `http://127.0.0.1:7351` and the line "console login: admin / password"
   marked local-only.

**`down.sh [-v]`** stops the stack; `-v` also drops the database volume (all local accounts and scores are gone; says so).

**Contract test (`tests/contract/run.sh`, same path and interface).** It no longer carries its own compose file; it calls the base compose with
`-p ironhold-contract --env-file "$repo/backend/.env"` on **every** compose call, including the `trap` cleanup, and exports `NAKAMA_PORT=7360`,
`NAKAMA_CONSOLE_PORT=7361`, `NAKAMA_MODULES="$here/modules"` (absolute: relative paths resolve against the first compose file's directory) and the default
7200 s token expiry. Its curl loop and `NAKAMA_URL` use `NAKAMA_PORT`; it waits with `up -d --wait`. The project name and the port are what let a running dev stack
coexist with a contract run, and what stop `down -v` in the trap from deleting the dev stack's database. The stale comment in `run.sh` that names 3.41.0 is replaced by a pointer to `backend/.env`.

**Line endings.** New `.gitattributes`: `*.sh text eol=lf`, `backend/.env text eol=lf`, `*.yml text eol=lf`. Existing CRLF shell scripts renormalise on the next touch; no other file types change.

**Safety.** Ports on 127.0.0.1 only (the console is published locally on purpose, to inspect leaderboards); Nakama's default keys and console credentials; no secrets in the folder;
the `ironhold-dev` project name plus the warning header and the `up.sh` banner are enough to tell it from a deployable config. Production and staging compose, vault secrets,
Traefik and Cloudflare stay in the homelab repo, whose deploy script takes `ironhold backend config` output.

**Out of scope:** a dev stack for a web build (Decision 2), CI, a `.ps1` twin (the repo's shell rule is Bash), any change to `server_config.rs`.

## Implementation notes (2026-11-05)

- The stale-CLI check is a warning, not an exit (file times are reset by a git checkout): `up.sh` compares the CLI's embedded `ironhold.lua` with the source and warns when they differ; the source module is always the one loaded.
- `up.sh` generates into a temporary folder and copies over `backend/modules/`; arguments are folder names under `assets/projects/`; the project scan reads each project's own `.project.ron` for `backend_path` set to a string; `-p ironhold-dev` and the ports are fixed inside the scripts so an inherited `COMPOSE_PROJECT_NAME`/`NAKAMA_PORT` cannot change them.
- One stack per machine: several worktrees share it (documented). `.gitattributes` also pins `.githooks/*` to LF.
- The printed command has no `--all-features` (`ironhold_native`'s only feature is `inspector`).
- Not verified: the browser's behaviour for an `https` page reaching `http://127.0.0.1` (the docs only say the hosted web build cannot use a local server).

## Acceptance criteria

- Given Docker is running, when a developer runs `backend/up.sh`, then Nakama and Postgres are healthy, `backend/modules/` holds the generated `ironhold_games.lua` and the **source** `ironhold.lua`,
  and the printed command, run literally, signs in against the local server.
- Given the stack is up, when `tests/contract/run.sh` runs, then it passes, uses other ports and its own project name, and the dev stack and its volume are not disturbed.
- Given the stack is up and a `backend.ron` changed, when `up.sh` runs again, then the module is regenerated, only the `nakama` container restarts and the database is intact.
- Given no Docker daemon or Docker not installed, when `up.sh` runs, then it exits non-zero with a message that names the cause and nothing is written; given a stale or missing CLI or port 7350 in use, the same with the specific fix.
- The Nakama and Postgres image tags appear in exactly one non-markdown file (`backend/.env`); `.sh`, `.env` and compose files have LF endings in the working tree.
- Docs: the `docs/README.md` row, the `docs/20` pointer with the web-build limitation and the local troubleshooting rows, the `docs/15` note and the root `README.md` pointer exist, and the README lists the prerequisites first.
