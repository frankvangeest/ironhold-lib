# Feature: Make `strafe_left` / `strafe_right` real, and make every `InputMap` key unbindable

_Status: In Progress (plan-reviewed 2026-10-16; Frank decided both open items the same day, see "Plan-review" at the end of this file)_
_Planned at: `eb56cf3` (2026-10-16)_

Prerequisite for `planning/features/first_person_starter.md` (v1 control schemes build on this). Split out so that branch's diff stays about first person, and so this one can be judged on one question only: **is every existing project's behaviour unchanged?**

## What
Today `InputMap.strafe_left` / `strafe_right` (defaults `KeyQ` / `KeyE`) are accepted, documented ("Strafe left (camera-relative)", `docs/20_data_formats.md` `InputMap` table) and written into shipped prefabs, but **nothing reads them** (`grep strafe_left` over `crates/ironhold_core/src` hits only `schema/player.rs`; `input_translator_system`, `runtime/input.rs:335-377`, uses only `left`/`right`, which turn unless `strafe_mouse_button` is held). This feature makes them real strafe bindings and makes every key field an `Option<String>` so a designer can unbind it with `None`, **without changing what any existing project does**.

## Why
- A designer who sets or rebinds `strafe_left` sees no effect and no warning (silent failure, already present in three shipped projects and the docs).
- `left`/`right` are a plain `String`: the only way to unbind is `""`, which `InputMap::parse_key` turns into "silently unbound" with no diagnostic.
- The first-person starter and any future control scheme (`controls: FirstPerson`, UX consult 2026-10-16) need strafe keys that work and bindings that can be cleared.

## Findings (verified at `eb56cf3`)
- Defaults `KeyQ`/`KeyE` (`schema/player.rs` `default_strafe_left_key`/`_right_key`) apply to **every player without an explicit `inputs:` block**. Wiring the fields while keeping those defaults would make Q/E strafe in every project that never asked for it. So the default must become **unbound** (`None`), not `KeyQ`/`KeyE`. That is the only way "wire them up" is behaviour-neutral.
- Shipped prefabs that write the fields explicitly (all currently no-ops, so wiring them would change behaviour): `3rd_person_game_demo/prefabs/prefabs.ron` (3 players, `KeyE`), `camera_modes/prefabs/prefabs.ron` (4 prefabs, `KeyQ`/`KeyE`), `local_coop_demo/prefabs/prefabs.ron` (19 `strafe_right` lines, including a P2 using `ArrowLeft` as `strafe_left` at ~line 412, and `scenes/room8.scene.ron`, which has a comment about P3's strafe key), plus CLI test fixtures under `crates/ironhold_cli/tests/fixtures/` and Rust tests (`ron_validation.rs:1779-1823` asserts the `KeyQ`/`KeyE` defaults and explicit values; others construct `InputMap` literals).
- **Collision:** `3rd_person_game_demo` players have `strafe_right: "KeyE"` while `main.scene.ron:509` has an action-bar slot on `key: "KeyE"`. Wired, E would strafe **and** fire the slot. This is the only slot using Q/E found by grep (`key: "e"|"E"|"q"|"Q"|"KeyE"|"KeyQ"` over `assets/projects`), but the audit must repeat it over bare-letter and per-scene keys.
- `local_coop_demo` P2 binds arrow keys: check whether `left`/`right` and `strafe_left`/`strafe_right` reuse the same key there (e.g. `left: "ArrowLeft"` **and** `strafe_left: "ArrowLeft"`); wired, that key would turn and strafe at once.

## Approach
1. **Schema (`schema/player.rs`):** `strafe_left`/`strafe_right: Option<String>`, default **`None`**. Convert `forward`, `backward`, `left`, `right`, `jump`, `run`, `interact`, `target_next` to `Option<String>` keeping their current defaults (`Some(..)`), so `None` unbinds. `ron_loader` has `implicit_some` on (`ron_loader.rs:98`), so `left: "KeyA"` still parses unchanged; verify with a parse test of every shipped project. `InputMap::key(name)` already returns `Option<KeyCode>`; callers need no change beyond the field types. `Default` impl and the `default_*` fns stay the single source (see the comment on `impl Default for InputMap`).
2. **Behaviour (`input_translator_system`):** strafe keys add to `move_vec.x` (right `+1`, left `-1`), additive with the existing A/D strafe-mode path and the left stick, then the existing `clamp_length_max(1.0)`. No change to `player_movement_system`. `left`/`right` stay "rotate unless strafe mouse button held"; docs now describe them as turn.
3. **Project audit (same change, behaviour-neutral):** for each shipped prefab that writes `strafe_left`/`strafe_right`, either **delete the line** (default is now unbound, behaviour identical to today) or, only where the designer clearly intended Q/E strafing (`camera_modes`? decide per prefab from its on-screen hint text), keep it and confirm no slot/other binding shares the key. Default decision: **delete from `3rd_person_game_demo` and `local_coop_demo`**, **keep in `camera_modes`** only if its hint labels advertise Q/E (check). Tests and CLI fixtures updated accordingly (`ron_validation.rs` default assertions become `None`).
4. **Diagnostics:**
   - `ironhold validate` (error unless noted): an unknown key name in any `InputMap` field (today silent); `""` (warn, suggest `None`).
   - Warn when one key is bound twice within an `InputMap` among movement/action keys, **including `left` and `strafe_left` sharing a key** (turn+strafe at once).
   - Warn when a movement key equals an action-bar slot `key` in a scene that instantiates that prefab (the `KeyE` case).
   - **Plan-review additions:** the collision check also covers `.project.ron` `global_key_bindings` and flycam movement keys (`FlyCamDef.down` defaults to `KeyQ`); it runs on the **resolved** bindings (so it stays correct when `controls:` schemes land, see `first_person_starter.md`); unknown-key checking also covers `look_*` and `target_next`, and distinguishes `""` (warn) from an unknown name (error) because `parse_key("")` also returns `None`. Placement: the movement-key-equals-slot-key check is a `--strict` `StrictWarning` like `claimed_gamepad_collision` (`validate.rs` ~3283). CLI fixtures `duplicate_gamepad_index_*` bind `ArrowLeft` to both `left` and `strafe_left` and will start producing the new warning: re-check any "no warnings" assertions.
   - Scoped like the existing duplicate-`gamepad_index` checks: `entities:` of each scene only, never the prefab catalog (`schema/CLAUDE.md`, "Duplicate `gamepad_index` / `player_index` checks are scoped to `entities:` on purpose").
5. **Docs:** correct `docs/20_data_formats.md` `InputMap` table (`left`/`right` = turn; strafe rows: default `None`, "strafe, **relative to the character's facing**" (not camera-relative: `player_movement_system` applies `Move` via `transform.forward()/right()`, `player.rs:567-570`); types become `Option<String>`; `None` unbinds). **Also fix every example that writes strafe keys (plan-review, UX #2):** the `inputs:` example blocks at ~lines 2374, 2488, 2749, 2765, 2856, 3034, 3111, 3139 (several bind one key to both turn and strafe: P2 `ArrowLeft`, P3 `KeyJ`, P4 `Numpad1`, which would turn **and** strafe once wired and trip the plan's own duplicate-key warning), the "Scheme" table at ~2478-2480 ("W/A/S/D, Q/E strafe"), and the note at ~3215. Fix the `run` row ("Hold to run"; it is a toggle today). Also add rows to `docs/15_authoring_tools.md` for each new `validate` check, mention in `docs/20` "Schema evolution" if applicable (no `schema_version` bump needed: parse-compatible, one default changed from a never-read value to `None`).

## Acceptance criteria
- Given any shipped project loaded before and after this change, then every player moves and turns exactly as before (no new Q/E movement in any project that did not already advertise it).
- Given a player prefab with `strafe_left: Some("KeyQ")`, when Q is held, then the character moves left relative to its facing without turning.
- Given a key field authored as `None`, then that binding does nothing and `validate` does not warn.
- Given an unknown key name or `""` in an `InputMap`, then `ironhold validate` reports it.
- Given a movement key and an action-bar slot key that are the same in a scene's instantiated prefab, then `ironhold validate` warns, naming both.
- Given `InputMap::default()`, then it equals an omitted `inputs:` block and `strafe_left`/`strafe_right` are `None`.
- Given `camera_modes` or `3rd_person_game_demo` is open, then pressing Q or E does nothing (checkable from a designer's chair; replaces "byte-identical").
- House style: RON examples write `"KeyQ"`, never `Some("KeyQ")` (`ron_lint`).

## Implementation notes (2026-10-16)
- **Flycam keys are deliberately excluded from `movement_key_slot_collision`** (the plan-review asked for them): a flycam shares WASD with the player on purpose (`camera_modes`' spectator room), so comparing them would only produce false positives. Slot keys, `scene_key_bindings` and `global_key_bindings` are compared; a player with no `inputs:` block is compared using `InputMap::default()`.
- **`target_next` keeps its historical fallback**: `None` turns keyboard cycling off, an unrecognised name still falls back to Tab (behaviour-neutral); the validate messages and docs say so.
- **One real shipped-project fix (behaviour change, found by the new check):** `local_coop_demo`'s P3 `look_right: "KeyP"` collided with `global_key_bindings["KeyP"] = toggle_pause`, so looking right paused the game. Changed to `"KeyY"` (unused in the project) in `prefabs.ron` and the keyboard-look table in `docs/20_data_formats.md`.
- **Follow-up (not in this change):** player `inputs:` key names have no runtime `warn!` (gamepad button names do, in `assemble_player_config`); only `ironhold validate` reports them. Logged as a backlog item.
