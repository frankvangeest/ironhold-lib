- [x] **Scroll-wheel orbit zoom snaps straight to `min_radius`/`max_radius` instead of stepping gradually** — one scroll-wheel step zoomed the `Orbit`/`Party` camera all the way in or out rather than by a small increment. Root cause (corrected from the original suspicion after 4 parallel post-implementation reviews independently verified it against winit's vendored source): the initial "Windows OS lines-per-notch setting" theory was wrong — winit derives a native `Line` notch directly from `WHEEL_DELTA`, always exactly `y = ±1.0`. The real mechanism is specific to the **browser** (this project's primary WebGPU target): Chrome/Edge report a standard wheel notch as `MouseScrollUnit::Pixel` (~100 logical px), which winit's web backend further multiplies by the page's `devicePixelRatio` before Bevy ever sees it — so one click could arrive as `y = 100..300+` depending on display scaling, blowing straight through `min_radius..max_radius` in `camera_orbit_system`'s/`party_camera_follow_system`'s unbounded `zoom_delta * zoom_speed * delta_secs()`. Fixed: a new `normalized_wheel_delta()` (`capabilities/camera.rs`) clamps **both** `Line` and `Pixel` events to ±1.0 per notch (not just scales `Pixel` down — DPI-dependent scaling alone doesn't remove the DPI dependence, confirmed independently by 2 reviewers against the source), filters non-finite (`NaN`/`inf`) deltas before clamping (`f32::clamp` passes `NaN` through unchanged, which would otherwise permanently poison `OrbitState.radius`), and caps the per-frame summed total at `MAX_WHEEL_NOTCHES_PER_FRAME` (3.0) to guard against `Time<Virtual>`'s 250ms `max_delta` amplifying a batched/hitched frame. A related bug found by the same review pass and fixed alongside it: `PartyState.manual_zoom_offset` accumulated unboundedly past what the radius clamp could ever use, banking a "dead reserve" that made a reversed scroll do nothing until enough notches burned through it — now re-derived from the clamped radius every frame. 10 regression tests (`local_coop_tests.rs`) cover both units, the per-event-vs-per-frame clamp distinction, fractional `Line` deltas, `NaN` handling, and the offset-rebanking fix; one test (`..._does_not_bank_past_the_radius_clamp`) initially failed for an unrelated reason — a loop of repeated `run_system_once` calls without draining `Messages<MouseWheel>` between them re-reads all historical events every call (a `MessageReader`'s cursor is per-system-instance state, discarded and reset by each fresh `run_system_once`) — rewritten to avoid the loop entirely. Full test suite (151 `local_coop_tests` + all other `ironhold_core` files) + `cargo check -p ironhold_cli` green; real-hardware playtest confirmed by Frank in `3rd_person_game_demo` and `local_coop_demo` — `6c830c7` (2026-08-11). ### Performance
- [ ] **Off-thread texture decode in WASM** — use the browser's `ImageBitmap` API to decode textures off the main WASM thread, eliminating main-thread stalls during asset loads; requires a `wasm32`-specific code path in the asset loading pipeline or a Bevy plugin that wraps `createImageBitmap`; investigate whether Bevy's current WASM asset pipeline already defers texture decode before implementing. Sourced from Phaser's web-optimised asset loader model.
- [ ] **Extend pipeline warmup to Text2d and UI pipelines** — spawn hidden warmup entities for `Text2d` and UI `Node` at scene load to pre-compile the 2D/UI GPU pipelines, eliminating WASM frame spikes on first text/UI render; design: `planning/features/pipeline_warmup_2d_ui.md`
- [ ] **Discrete LOD steps for depth-scaled label font sizes** — snap `base_font_size * scale` to a small fixed set (e.g. 100 %, 75 %, 50 %, 25 %) instead of rounding to every integer; bounds atlas slot count to ~4 per label regardless of depth range, at the cost of a slight stepping artefact on slow zoom. Integer rounding + 0.5-threshold guard already fix the per-frame atlas upload problem; this is a further atlas-memory micro-optimisation.
- [ ] **Scene transition material cache** — `scene_loader` rebuilds all materials in the asset catalog on every `LoadScene`, including materials already built for the previous scene; cache built handles per-project in a persistent resource and only rebuild when the catalog key set changes; estimated 50–200 ms saving per transition on large projects (`scene_loader.rs` material rebuild block)
- [ ] **WASM terrain generation first-frame stall** — `AsyncComputeTaskPool` degrades to `block_on` on the main thread in WASM, causing 100–500 ms jank on first frame for large heightmaps; fix by splitting mesh generation across multiple frames (progressive tile-by-tile build) or pre-baking terrain meshes as GLB assets; requires `#[cfg(target_arch = "wasm32")]` code path (`terrain.rs` poll system)
- [ ] **Per-frame collection allocations in hot systems** — `stat_modifier_system` (key clone Vec), `message_interpreter_system` (event Vec rebuilt each frame), and `player_movement_system` (input HashMap) each allocate new collections every frame; refactor to reuse pre-allocated collections via `.clear()` on a `Local` resource or avoid the intermediate collection entirely; WASM GC pressure is higher than native so the gain is larger there

The real mechanism is specific to the **browser** (this project's primary WebGPU target): Chrome/Edge report a standard wheel notch as `MouseScrollUnit::Pixel` (~100 logical px), which winit's web backend further multiplies by the page's `devicePixelRatio` before Bevy ever sees it — so one click could arrive as `y = 100..300+` depending on display scaling, blowing straight through `min_radius..max_radius` in `camera_orbit_system`'s/`party_camera_follow_system`'s unbounded `zoom_delta * zoom_speed * delta_secs()`. Fixed: a new `normalized_wheel_delta()` (`capabilities/camera.rs`) clamps **both** `Line` and `Pixel` events to ±1.0 per notch (not just scales `Pixel` down — DPI-dependent scaling alone doesn't remove the DPI dependence, confirmed independently by 2 reviewers against the source), filters non-finite (`NaN`/`inf`) deltas before clamping (`f32::clamp` passes `NaN` through unchanged, which would otherwise permanently poison `OrbitState.radius`), and caps the per-frame summed total at `MAX_WHEEL_NOTCHES_PER_FRAME` (3.0) to guard against `Time<Virtual>`'s 250ms `max_delta` amplifying a batched/hitched frame. A related bug found by the same review pass and fixed alongside it: `PartyState.manual_zoom_offset` accumulated unboundedly past what the radius clamp could ever use, banking a "dead reserve" that made a reversed scroll do nothing until enough notches burned through it — now re-derived from the clamped radius every frame. 10 regression tests (`local_coop_tests.rs`) cover both units, the per-event-vs-per-frame clamp distinction, fractional `Line` deltas, `NaN` handling, and the offset-rebanking fix; one test (`..._does_not_bank_past_the_radius_clamp`) initially failed for an unrelated reason — a loop of repeated `run_system_once` calls without draining `Messages<MouseWheel>` between them re-reads all historical events every call (a `MessageReader`'s cursor is per-system-instance state, discarded and reset by each fresh `run_system_once`) — rewritten to avoid the loop entirely.
