`world_label_screen_pos_system` (`crates/ironhold_core/src/lib.rs`, ~L507) runs every Update. Projects each `WorldLabel` through the active `Camera3d` whose viewport rect contains it (viewport-aware fix for split-screen; replaced old `.single()` that early-returned on 2+ cameras).

Per-frame cost profile:
- Collects `camera.is_active` cameras into a `Vec` then `sort_by_key`. Vec holds **borrowed** tuples `(Entity, &Camera, &GlobalTransform, Option<&SplitViewportSlot>)` — size <=4 (MAX_SPLIT_PLAYERS=4), 1 in normal scenes. One tiny malloc/frame.
- Per label: selection is now `filter_map(...).nth(rank)` (was `find_map`, first hit) over the <=4-camera Vec (`world_to_viewport` + `logical_viewport_rect` + `rect.contains`). Lazy iterator, no alloc, short-circuits at rank-th qualifying camera. Total O(N labels × M cameras), M<=4 → linear, **no quadratic path**. M=1 in single-cam scenes = zero regression.

**2026-07-10 amendment (WorldLabelRank):** `runtime/scene_manager/mod.rs` added `WorldLabelRank(pub u8)`; rank absent == rank 0. Two spawn sites in `scene_loader.rs` now spawn MAX_SPLIT_PLAYERS(4) sibling entities per authored label (ranks 0..3) so a point visible in 2+ split viewports shows in each: the scene-level `world_labels:` loop, **and** the per-entity `label:`/`EntityLabelDef` (`pending_labels`) loop — the latter was missed on the first pass (perf-reviewed only the `world_labels:` site) and is actually the one `local_coop_demo`'s portal room-name labels use in practice (`tracked_entity`, not fixed `world_pos`). Nameplates/damage-popups/stat labels unchanged (single-instance, implicit rank 0). Cost: 4x entities + 4x per-frame projection **scoped to these two label-producing sites only** — one-time 4x spawn at scene load (4x Text2d + text String clone, negligible), per-frame bounded at <=16 projection calls/authored label. Reviewed OK for web. `WorldLabelRank(u8)` is zero-size-impact, no new deps.

**2026-07-12 amendment (Phase 3 nameplate distance culling):** query gained `Option<&mut NameplateCameraDistance>` term; on the success path (and every early-return: tracked gone/hidden, no qualifying camera) it stashes/clears `dist_to_selected_camera` for the anchor. The `(world_pos - cam.translation()).length()` (one sqrt) was **hoisted out** of the `if let Some(depth_scale)` block to run unconditionally once per label, shared by both the depth_scale font-scale and the new stash. Net cost: labels with neither depth_scale nor NameplateCameraDistance now pay one extra sqrt/frame (was skipped before) — negligible at realistic label counts. `Option<&mut T>` query terms are fully WASM-safe (single-threaded, no atomics); None-archetypes skip the write at zero cost. Zero new deps; `NameplateCameraDistance(Option<f32>)` is trivial size. Reader is [[project_nameplate_system]]'s `nameplate_visibility_system`, ordered `.after` this.

**2026-07-12 amendment (Phase 4 stat-widget duplication):** `WorldLabelRank` duplication extended from world_labels/label to `stat_label` + Ascii `world_stat_bar` (fill+bg Text2d), gated on `is_split_screen` (scene-loader: `player_configs.first().camera.split.is_some()`; `drain_dynamic_stat_ui_system`: `ActiveSplitScreen.0.is_some() || DynamicSplitConfig.0.is_some()`). Single-cam scenes get ranks=1 (0 regression). Split scenes get MAX_SPLIT_PLAYERS=4 ranks each. Consequence for THIS system: 4x WorldLabel entities in split scenes → 4x per-frame projection, unchanged code, bounded ≤4 cams each (short-circuits at nth). Heavy wave-spawn split scene (dozens of enemies w/ bars) scales projection calls; deliberate gated cost. See [[project_stat_widget_split_duplication]] for the bigger per-frame `format!` concern in the update systems (they iterate 4x entities incl. hidden ranks).

**2026-08-15 amendment (nameplate-zoom-spacing — anchor `Transform.scale` depth scaling):** the depth-scale block became an `if let Some(text_font) { …font_size… } else { …Transform.scale… }`. The new `else` arm fires only for WorldLabel entities with **no `TextFont`** — i.e. genuinely anchor-style ones (nameplate anchor, Pixel/Icon/Textured `world_stat_bar` anchors). Bevy's `Text2d` *requires* `TextFont`, so damage popups / stat_label / Ascii bars can never fall into the else arm; the two branches are cleanly disjoint.
- Cost of the else arm: ~9 scalar f32 ops (max/div/min/max/sub/abs/cmp), no alloc, no sqrt (distance already hoisted). Under ~5% of the pre-existing per-label cost, which is dominated by `world_to_viewport` (mat4 + perspective divide) per camera. Non-issue even at hundreds of labels.
- **No extra transform-propagation cost vs. the position guard it mirrors.** Both writes go through the *same* `Mut<Transform>` change tick — dirtying twice in one frame is idempotent. On frame 1 the anchor is `Added` and propagates regardless. Moving camera → position guard already fires, scale write is free. Idle → neither fires (distance constant), tree stays clean. The only genuinely-new dirty case is a camera dollying toward a label near screen centre (distance changes, screen pos doesn't) — intended, bounded.
- **SUPERSEDED 2026-08-16 (same feature branch, round 2):** anchors are no longer `depth_scale: None`. `nameplate_setup_system` (via `resolve_label_depth_scale(LoadedLabelDepthScale, None)`) and all Pixel/Icon/Textured bar anchors now inherit `ctx.depth_scale`, so the `Transform.scale` else-arm is **live** in every scene with a `label_depth_scale:` block (7 today: 3rd_person_game_demo, custom_materials, effect_mayhem_demo, particles_demo x2, primitive_world, stats_demo). Still guarded at 0.005 and usually shares the position write's dirty tick. Scenes without the block remain at `None` → free.
- Also round 2: `WorldLabel.screen_offset` is multiplied by `depth_scale_factor(...)` unconditionally (2 extra f32 muls/label/frame; `depth_scale_factor` is then called twice per label on the anchor path — pure/`#[inline]`, LLVM CSEs it; hoisting it above the if/else is a readability win, not a perf one). New `StatLabelDef.screen_offset`/`WorldStatBarDef.screen_offset` are spawn-time only.
- **(historical, pre-round-2) `depth_scale: None` anchors were provably free**: all anchor spawn sites use `Transform::default()` (scale exactly `Vec3::ONE`) and nothing else writes anchor scale (`world_pixel_bar_update_system` writes the *fill child*, not the anchor). So the `1.0` fallback compares `0.0 >= 0.005` → never writes, ever. `local_coop_demo` (nameplates, no `label_depth_scale`, 4x rank duplication) is unaffected at zero cost.
- **This path is cheaper than the font-size path it parallels**: changing `TextFont.font_size` marks `Changed<TextFont>` → `update_text2d_layout` + new `FontAtlasSet` glyph rasterization per distinct rounded size (hence the `.round()`). `Transform.scale` does none of that — no atlas churn, no re-layout. Prefer the scale mechanism for any future anchor-style widget.
- **Nit ADOPTED 2026-08-16:** the scale write is now XY-only (`t.scale.x`/`t.scale.y`), Z untouched — the z-layering/flicker concern below is resolved; do not re-raise. Original wording: the write was `Vec3::splat(s)`, which scaled **Z** too. Nameplate children use z 2/3/9/10 for intra-widget layering; compressing them per-distance makes 2D transparent sort order between *different* anchors distance-dependent (flicker risk on overlap, and `min_scale` defaults to `0.0` → degenerate zero-scale affine if a designer omits it). `Vec3::new(s, s, 1.0)` fixes both for free. Raised 2026-08-15; check whether it was adopted before re-raising.

**Why:** the natural allocation-avoidance instinct (hoist to `Local<Vec<_>>`) does NOT apply here — the Vec stores references borrowed from the query, which cannot outlive the system call, so a `Local` can't hold them across frames. Would require storing owned `Entity` ids + re-fetching, more complex than the <=4-elem alloc it saves.

**How to apply:** treat the per-frame <=4 Vec+sort as negligible; do not recommend `Local` reuse for it. Transform/font writes are already change-detection guarded (>=0.5px). Zero new deps. Related: [[project_split_screen_hud_labels]].
