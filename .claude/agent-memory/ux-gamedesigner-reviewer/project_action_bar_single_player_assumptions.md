The `ActionBar` UI widget carries three single-player assumptions that are durable engine facts (verify against current code before citing, but true as of 2026-07-15). They all become designer-visible traps the moment a scene has 2+ players, and they are the crux of `per_player_split_screen_targeting.md` Phase 2.

- **~~Keyboard-only~~ — FIXED 2026-07-31 by `gamepad_action_bar_slots`.** `ActionSlotDef.gamepad_key: Option<String>` now also fires a slot from the **owning player's own** pad (`owner_player` → that player's `InputMap.gamepad_index`, via `resolve_gamepad`), never any connected pad. Keyboard `key` stays required and stays globally shared — a "pure gamepad" slot is still unauthorable. Gamepad presses emit the **same** `action_bar.*:{key}`/`intent.slot.{key}` events (identity is always `key`), so no rule rewiring is needed. **CLOSED:** `gamepad_key` set while the owning player has no `gamepad_index` is now a hard `ironhold_cli validate` error (`gamepad_key_without_gamepad_index`, `validate.rs` ~769) — no longer silently inert/undocumented. **Still open:** `gamepad_key` equal to that player's own `gamepad_jump`/`run`/`interact`/`target_next` (defaults South/East/West/North) = one press does both, entirely unchecked. The docs' own worked example and local_coop_demo room3's uncomment instructions both pick `"South"`, i.e. they walk the designer straight into this collision. See [[warn-vs-silent-fallback-principle]].
- **Cost pool is global.** `SlotCost` checks/deducts against the single global `LoadedStats` resource, NOT per-entity `StatMap` (the `"{self}.stat"` addressing NPCs use). In a two-bar split-screen scene, spending a cost stat dims BOTH bars — a false per-player signal, not just a "shared economy" limitation.
- **`slot_key` is scene-wide identity.** `CooldownMap`/`PendingIntentActions`/`HandledIntentSlots` are keyed by the bare `slot_key` string across the whole scene, not per bar/player. Two bars reusing the same key (the natural copy-paste path) collide: fire-first + shared cooldown bleed.

**Also:** intent interception (`intent.slot.{key}` rules in `rules.ron`) is a first-class, doc-encouraged pattern (`docs/20_data_formats.md` ~L912-929, incl. a `{target}`-using "redirect" example), but `{target}` inside those rules resolves via the interpreter against the PRIMARY player only (`CurrentTarget`) — so the encouraged pattern is the one that silently breaks in co-op. The `intent.slot.{key}:{player_id}` event suffix lets a rule match WHICH player pressed, but not target that player. See [[per-player-targeting-gating]].

**`ActionSlotDef.key` is REQUIRED (`String`, not `Option`) — there is no unbound or gamepad-only slot.** Every slot always carries a live binding on the single global shared keyboard, regardless of the bar's `owner_player`. Consequence for the mixed keyboard+gamepad co-op config: a gamepad player's slot still needs a `key`, and any keyboard press of that key fires it (acting on the gamepad player's own target). `gamepad_action_bar_slots` (shipped) added the optional sibling `gamepad_key` but did NOT make `key` optional — so a "pure gamepad" slot remains unauthorable and the phantom keyboard binding persists. Docs are now explicit about this ("Stays keyboard-only and required even for a gamepad-routed slot").

**`gamepad_key` has no glyph support.** `key_hint` has no gamepad-button mode, so a gamepad-routed slot's corner glyph is still the keyboard `key`'s pretty-print unless the designer hand-authors `key_hint`. Correctly flagged in docs as a known limitation.

**Doc-location trap:** the section a designer actually reads for co-op bars is "Per-player action bars (split-screen)" (`docs/20_data_formats.md` ~L1099, the target of `owner_player`'s own "full RON example is below" pointer). The gamepad callout sits ~140 lines EARLIER, under `SlotCost`. Any new per-player action-bar feature must add a pointer in the L1099 section or designers will never find it.

**How to apply:** when reviewing any co-op/split-screen action-bar change, check the demo isn't cost-gated (cost pool is per-entity as of `per_player_stat_pools`; room3 uses per-player mana, so the old dimming artifact point is stale), and uses disjoint slot keys (cross-bar duplicate keyboard detection exists via `warn_cross_bar_duplicate_keys`, and the stale "not currently cross-checked" doc claim is now FIXED — docs cite `error_type: "cross_bar_duplicate_key"`). Push for load-time `warn!`s (not just opt-in CLI `validate()`): a designer with only `assets/` + a hosted WASM build **cannot run `ironhold validate` at all**, so "flagged by validate" is not a designer-reachable diagnostic — the browser console is.
