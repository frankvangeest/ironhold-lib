`NpcState` (capabilities/npc.rs) is a **runtime enum, never serialized** — adding a variant is NOT a schema change and never breaks RON backward-compat. NPC *tuning* values go into `NpcDef` schema with `default_npc_*` named-default fns (catalog.rs ~1065-1086 pattern); NPC *states* stay in Rust. Keep this split.

**Investigating-state design — SHIPPED** (proposed 2026-06-19, Frank's team; confirmed present in `capabilities/npc.rs`): `NpcState::Investigating` exists between Chase and Return for hit-from-range kiting, reached from both the detect/chase transition logic and its own timeout/leave-range handling. The architecturally important decision landed as designed: Chase reverted to **visibility-only** `in_chase`, and the old `dist_opt.or(target_dist_opt)` hack that stretched Chase to cover beyond-visual-range pursuit is gone — `dist_opt` is now a plain `visible.map(|(_, _, d)| d)` read, no `.or()` fallback. Chase = live visible entity; Investigating = walk toward a stale last-known position. Kept as separate states from Return (which means "go home to origin"), as recommended.

**Why:** overloading Return/Chase with mode flags conflates runtime states and raises cognitive load; the existing duplicated `was_hit` check (npc.rs ~237 and ~292) is already a smell. Centralize hit-handling into one pre-match block instead of per-state arms.

**How to apply:** if reviewing NPC AI changes — (1) new states are fine, not schema breaks; (2) push for centralized hit/aggro handling not per-arm duplication; (3) snapshot attacker pos in `npc_hit_relay_system` (Update, closest to the hit event) not in `npc_behavior_system` (FixedUpdate, 1+ tick later — see [[schedule-update-vs-fixedupdate]]); (4) Rapier ray casts already make this non-deterministic — don't claim determinism (see [[determinism-networking]]). `NpcHitQueue` HashMap<String,Vec3> swap and Option<Vec3> on NpcAgent are perf-trivial at 2-8 NPCs/scene.

**Dead-state movement latency (reviewed 2026-06-19):** routing death detection through the relay-queue round-trip adds multi-frame latency (stat_threshold_system emits depleted next-frame per lib.rs comment → relay sets NpcDeadQueue → FixedUpdate already ran → drains 1-2 frames later), so the spider keeps running its Chase movement for a tick or two after dying. Architectural fix: detect health<=0 at the TOP of npc_behavior_system's per-NPC loop (it already queries the entity) and set NpcState::Dead + zero velocity in the same tick — do NOT gate movement-stop on the event/queue path. The relay/queue may still drive the RON *event* side; it must not be the thing that stops the body. Stopping = `velocity.linvel = 0.0` not `*= drag` (drag only asymptotes, never reaches zero).

**Death/corpse animation (reviewed 2026-06-19):** `looping: false` on an AnimationOverrideDef does NOT hold the last frame — `duration:`/`expires_at` is what controls expiry (animation_resolver_system step 1). For an indefinite corpse pose: omit `duration` (so expires_at=None) AND keep `cancel_on_move: false`; the override stays forever and `should_loop:false` holds the clip's last pose. Clear it via `stop_action:` (resolver matches it BEFORE the priority gate, so it clears even priority-150). Drive the animation-clear from the SAME signal as the FSM revive (`npc.revive:{id}` → NpcReviveQueue) so state and animation can't desync into a moving-corpse / frozen-alive split. The stop-action token (e.g. `npc_revive`) must not collide with any real GLB clip/alias name.
