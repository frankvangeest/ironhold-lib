Three floating world-space widget systems exist/planned above 3D entities. They split into TWO categories, not three points on one spectrum:

- **Per-prefab authoring primitives** — `stat_label` (StatLabelDef) and `world_stat_bar` (WorldStatBarDef, has Ascii + Pixel styles). Authored on `PrefabDef` as `Option<...>`, single-instance, always-visible, no scene context, spawn inline at entity-spawn (and via `DynamicStatUiQueue` for `Action::Spawn`). Implemented in `capabilities/stat_display.rs`.
- **Scene-managed policy** — nameplate system (planned, `planning/features/nameplate_system.md`). Defining trait is its LIFECYCLE/POLICY: deferred spawn post-`SceneEvent::Ready`, scene-wide opt-in (`show_nameplates`), faction filter, per-frame distance culling via `NameplateSceneConfig` resource.

**Decision (advised 2026-06-23): partial consolidation, not full.** The only genuine duplication is the pixel-bar fill primitive. `WorldPixelBarFillMarker` + `world_pixel_bar_update_system` in stat_display.rs (lines ~201-261) already do left-anchored ratio→fill-width + color-band selection. The nameplate must REUSE this marker/system, not reimplement `NameplateBar`/`nameplate_update_system`.

**Why:** Full consolidation would pollute the simple case (training-dummy bar) with scene-level policy config, force the inline + DynamicStatUiQueue spawn paths to learn the deferred lifecycle, and produce one wide multi-mode struct instead of cohesive systems. "Fewer systems" is illusory.

**How to apply (boundaries to enforce):**
- `stat_label`/`world_stat_bar` NEVER read scene-level config. A field needing scene context is a signal it belongs in nameplate.
- Nameplate owns visibility policy; the fill-update system owns rendering only — it must never learn distance/faction. Visibility = `Visibility::Hidden` toggled separately.
- One pixel-bar fill primitive (`WorldPixelBarFillMarker`), one fill-update system. A 4th consumer (boss bar) reuses it.
- `StatLabelMarker` (live stat readout, updates each frame) stays distinct from nameplate static name `Text2d` (display name, set once). Looks similar, different meaning.

**Open risks flagged for the feature file:**
- Screen-pixel (world_stat_bar Pixel) vs world-unit (nameplate) `full_width` semantics both feed the same marker field — resolve coordinate-space convention before coding.
- Dynamic-spawn parity gap: nameplates spawn off SceneEvent::Ready so wave-spawned (`Action::Spawn`) entities get none. Recommend setup system poll for NameplateTag-without-anchor, not just on Ready.
- Nameplate scene-config + per-prefab `Option<bool>` override should mirror the existing `label_depth_scale` (scene) + `depth_scale: Option<bool>` (per-prefab) idiom in scene_v2.rs/catalog.rs — don't invent a new override pattern.
- Reusing ColorMaterial/Mesh2d means nameplate bars share the WASM render pipeline with world_stat_bar Pixel bars → zero new pipeline variants when a scene already uses Pixel bars.

Drift hazard: WorldStatBarDef and NameplateOptionsDef.StatBarDef describe the same concept in two structs — same class of bug as [[fragile_modules]] EffectDef/LayerDef sync. Mitigation: both construct the SAME runtime WorldPixelBarFillMarker; the single update system is the sync point.

**stat_label/world_stat_bar SPAWN topology (verified 2026-07-17) — the widget entity spawning is duplicated and player-blind:** It's a two-phase pattern in `scene_loader.rs`. Phase A = 3 collector sites (`:387` composite-GLB, `:592` single-primitive-mesh, `:657` single-GLB-actor) push `(entity, resolved_key, def)` into `pending_stat_labels`/`pending_world_bars` Vecs — NONE are player sites. Phase B = two loops (`:1023` stat labels, `:1067` world bars, ~160 lines incl. Ascii + Pixel branches) drain the Vecs and spawn the Text2d/Mesh2d + marker entities. The 4th site, `drain_dynamic_stat_ui_system` (`:2679`, fed by `DynamicStatUiQueue` for `Action::Spawn`), is a near-BYTE-FOR-BYTE copy of Phase B. So the real duplication to kill is Phase-B-loops vs drain-system (exists today, independent of players). `resolve_stat` (stat_display.rs) is already fully generic (LoadedStats global OR per-entity StatMap) — the visual/update side needs NO changes for players.

**Player wiring gap + recommended fix (advised 2026-07-17):** Players get NO stat_label/world_stat_bar — `PlayerConfig` doesn't carry the fields and neither player path (GLB `spawn_player_entity_core`, primitive inline) collects them. Recommended: (1) extract `spawn_stat_label_widget`/`spawn_world_stat_bar_widget` into stat_display.rs (correct home — rendering-only, no scene knowledge), refactor BOTH Phase-B loops and the drain system to call them (pure no-behavior refactor, kills the ~160-line copy); (2) add `stat_label`/`world_stat_bar` to `PlayerConfig` (forward in `assemble_player_config` like `material`/`stat_templates`) and have `spawn_player_entity_core` push a `DynamicStatUiEntry` to `DynamicStatUiQueue` — the drain path already owns `SceneMaterialParams` (Mesh + ColorMaterial assets), so routing players through the queue avoids threading Assets into the player spawn chain (Pixel bars need them; stat_label/Ascii don't). For GLB players the entity doesn't exist at Phase-A collection time, so you CANNOT just repeat the collector pattern — the queue/deferred push is the natural fit and is LESS work than repeating per-site. See [[stat_ownership_global_vs_instance]], [[player_spawn_paths]].

**World-space atlas-icon rendering — use `Sprite` + `TextureAtlas`, not custom mesh/material (advised 2026-07-17, plan-review of `world_icon_stat_bar.md`):** The existing icon-atlas convention (`ItemDef`/`ActionBarDef`/inventory) renders via `ImageNode` + `TextureAtlas`, which is bevy_ui / UI-camera ONLY — it cannot billboard-follow a world entity. The idiomatic world-space equivalent in Bevy 0.18 is the **`Sprite` component with `texture_atlas: Some(TextureAtlas { layout, index })`** (same `TextureAtlas` type UI already uses; `TextureAtlasLayout::from_grid` cache identical to inventory/shop). Sprite renders on the SAME Camera2d as the existing Text2d(Ascii)/Mesh2d(Pixel) world-stat-bar children, so it drops straight into the `WorldLabel` anchor + children hierarchy. Fill/empty (or any atlas cell) swap = write `sprite.texture_atlas.index` (change-detection-guarded) — no material handle, no mesh rebuild. This BEATS both options the icon-bar plan listed: (a) custom mesh with cropped UVs + textured `ColorMaterial`, and (b) a custom UV-offset `Material2d`. The only edge (a) has is reusing the already-warm ColorMaterial pipeline (zero new WebGPU pipeline); Sprite introduces the standard 2D sprite pipeline as the engine's first Sprite user → one lazy pipeline compile, absorbed into scene-load (world bars spawn in Phase B) and warmable via the existing offscreen-warmup pattern. Reject (b) outright (bespoke shader + new pipeline + most code, no benefit over (a)). Net: Sprite for simplicity + convention reuse; (a) only if a web build shows an unwarmable sprite-pipeline stall.

**Camera2d world-label children live in SCREEN-PIXEL space, not metres (verified 2026-07-17):** `world_label_screen_pos_system` sets the anchor `Transform.translation` to viewport coords (`vp.x - half_w`, `half_h - vp.y`). Camera2d is 1 unit = 1 px, so every child offset/size (Pixel bar `size`, icon `spacing`/cell size) is screen pixels — constant on-screen regardless of camera distance (that's WHY Pixel bars are excluded from depth scaling: anchor `depth_scale: None`). Any new world-stat-bar style must document its size/spacing fields as screen pixels, matching `Pixel`'s `size` doc — NOT "metres" (a recurring plan-authoring mental-model slip).

**Depth scaling has TWO mechanisms as of `feature/nameplate-zoom-spacing` (2026-08-14):** `world_label_screen_pos_system` (`lib.rs`) branches on `Option<&TextFont>` presence on the `WorldLabel` entity itself. Text2d-bearing labels (`world_labels:`, entity `label:`, `stat_label`, Ascii bar) scale `TextFont.font_size` (crisp re-rasterization, guard ≥0.5). Anchor-style labels with NO TextFont of their own (nameplate anchor, Pixel/Icon/Textured bar anchors) scale the whole child subtree via the anchor's `Transform.scale` (guard ≥0.005, `Vec3::splat`). Consequences to remember: (a) the `Transform.scale` path is a *minification* of the already-rasterized glyph atlas, so anchor-style name text goes slightly soft where a font-size-path label stays crisp — this is why the two branches must NOT be unified into one representation; (b) the discriminator is **implicit** (component presence, not an explicit mode) — putting a `TextFont` directly on a nameplate anchor in some future refactor would silently switch the whole widget back to font-scaling and stop scaling its Mesh2d bars; (c) `WorldLabel.base_font_size` is vestigial on anchor-style labels (set to `1.0`, never read by the scale path). (Superseded 2026-08-16: all four bar styles now pass `depth_scale: ctx.depth_scale` on that branch, so the anchor path is no longer nameplate-only.) `resolve_label_depth_scale` lives in `scene_loader.rs` (made `pub(crate)` for the nameplate call) but has 7 call sites across 3 modules — it belongs beside `LoadedLabelDepthScale`/`should_insert_nameplate` in `scene_manager/mod.rs`.

**SHIPPED on `feature/nameplate-zoom-spacing` round 2 (reviewed 2026-08-16) — four facts to preserve:**
- **`screen_offset` values are calibrated to be behavior-IDENTICAL to the old world offsets at exactly `reference_distance`.** `3rd_person_game_demo`'s numbers (29px / 50px for the old 2.8/3.1 vs nameplate 2.4) = old world delta × ~72 px/metre at `reference_distance: 12.0`, and the depth factor is exactly 1.0 there. So the fix is a no-op at ref distance, matches the old projection across the whole 12–24 m band, and only diverges (correctly, staying constant) closer in. Don't "simplify" those numbers — they encode that invariant. Caveat: 72 px/m is a function of FOV (60°) and viewport height (~1000px); the RON comment states it as if it were stable.
- **Screen-space stacking also silently fixed a split-screen bug.** Widget *sizes* (`font_size`, Pixel `size`) were already screen-pixel/viewport-independent while world-offset *spacing* scaled with viewport height — so in a half-height split viewport the stack used to compress around same-size widgets. `screen_offset` puts spacing and size in one coordinate space.
- **New single-writer claim:** `world_label_screen_pos_system` now owns `Transform.scale.{x,y}` of every no-`TextFont` `WorldLabel` whenever depth scaling is on (the in-code comment only documents the `depth_scale: None` no-op case). A future feature must not co-own anchor scale. Z is deliberately excluded to stop two differently-scaled anchors interleaving their Camera2d child z-ranges.
- **Behavior change to shipped example projects, baselines NOT auto-refreshed:** `Pixel`/`Icon`/`Textured` anchors went from hardcoded `depth_scale: None` to `ctx.depth_scale`, so `primitive_world` (25.0/0.4) and `stats_demo` (20.0/0.5) bars now shrink where they were size-locked. Any change to the anchor-scale path needs `python test_web.py --skip-build` + baseline review for those two, not just `3rd_person_game_demo`.

**Per-entity widget-stack spacing = `WorldLabel.screen_offset`, and it MUST be depth-scaled (advised 2026-08-16, `feature/nameplate-zoom-spacing` 2nd root cause):** one entity's nameplate + `stat_label` + `world_stat_bar` are three INDEPENDENT `WorldLabel` entities, each projected separately; near-identical world `offset`s (2.4/2.8/3.1) project to a huge pixel gap when zoomed in and collapse when zoomed out. Fix shape: designer-facing `screen_offset: (f32,f32)` on `StatLabelDef`/`WorldStatBarDef` (both live in `schema/catalog.rs`, per-prefab — NOT scene_v2.rs), same world `offset` for all three, stack in pixels. Non-obvious constraint: `label.screen_offset` is currently added raw in `world_label_screen_pos_system`, so a fixed pixel stack would NOT shrink with the widgets the depth-scale fix now shrinks — nameplate's own internal `bar_y` children DO shrink (they're local-space children of an anchor whose `Transform.scale` is depth-scaled). To actually mirror nameplate, multiply `screen_offset` by `depth_scale_factor(label.depth_scale, dist)`; safe because the only other consumer (damage-popup ±1px shadows, `action_executor.rs`) passes `depth_scale: None` → factor 1.0. Do NOT add this to `NameplateOptionsDef` (scene-wide, and it's the anchor everything else stacks around), and do NOT parent stat widgets to the nameplate anchor — nameplate anchors are single-instance rank 0 while stat widgets rank-duplicate per split viewport.

**world_stat_bar style taxonomy = 3 orthogonal production looks + 1 debug (planned, `world_textured_stat_bar.md` advised 2026-07-17):** flat solid = `Pixel` (shipped, Mesh2d+ColorMaterial), discrete pips = `Icon` (planned, Sprite+TextureAtlas), textured-continuous = `Textured` (planned, sliced Sprite), + `Ascii` (retiring debug default). Don't conflate `Textured` with `Icon` — Frank's "rounded health bar, begin/middle/end sprite" is CONTINUOUS fill (Pixel-shaped), NOT hearts. `Textured` is architecturally Pixel-with-a-9-sliced-Sprite-instead-of-a-flat-quad.

**Bevy 0.18 has built-in 9-slice: `Sprite.image_mode = SpriteImageMode::Sliced(TextureSlicer)` (verified against vendored bevy_sprite-0.18.0):** `TextureSlicer { border: BorderRect{min_inset,max_inset}, center_scale_mode, sides_scale_mode: SliceScaleMode::{Stretch|Tile}, max_corner_scale }`; `BorderRect` insets are in TEXTURE pixels. Continuous textured fill = drive `Sprite.custom_size.x = ratio*width` (the textured analog of Pixel's `Transform.scale.x`) — NOT scale.x (distorts caps), NOT `Sprite.rect` crop (clips right cap flat). A sliced sprite renders on the SAME standard 2D sprite pipeline as a plain Sprite (`compute_slices` just emits more quads) → no distinct pipeline, same first-Sprite-use WASM risk as Icon. Low-fill: `min_coef = coef.x.min(coef.y).min(max_corner_scale)` scales corners DOWN (caps un-round) rather than clipping — benign, document it. Textured's WASM fallback is WEAKER than Icon's (no clean 9-sliced degraded mode; ColorMaterial.texture quad under scale.x re-distorts) → mitigation is sequence-after-Icon, not a drop-in fallback. Reuse shared `fill_color`/`color_bands` as `Sprite.color` tint (default green would double-tint pre-coloured art → doc "set fill_color to white"). Recommend SEPARATE `Textured` variant, not a Pixel texture field (Pixel's border/bg_color flat quads are meaningless when art supplies the frame; update code diverges Mesh2d→Sprite).

**`StatWidgetSpawnCtx` has NO AssetServer/AssetCatalog today (only meshes+color_materials) — both Icon AND Textured need image handles:** resolve catalog key→path→`asset_server.load` (pattern in `capabilities/particle.rs:126`). Extend the ctx ONCE, coordinate the two features. Both call sites (scene_loader Phase B + drain_dynamic_stat_ui_system) already have AssetServer+catalog in scope.

**Textured style SHIPPED (reviewed 2026-07-18) — three non-obvious facts to preserve:**
- **Change-detection guard is load-bearing for a Bevy-internal system, not just efficiency.** `world_textured_bar_update_system` writes `Sprite.custom_size`/`Sprite.color` only inside `>0.5px` / color-inequality guards (reads via Deref, writes via DerefMut only when changed). This is CRITICAL because bevy_sprite_render-0.18.0's `compute_slices_on_sprite_change` re-runs 9-slice on `Changed<Sprite>`. A naive unguarded write would re-slice every textured bar every frame (real WASM cost). A future maintainer "simplifying" the guard would silently reintroduce per-frame reslicing. Verified against vendored `computed_slices.rs`: `compute_sprite_slices` uses `sprite.rect.unwrap_or(full image)` as the slice `texture_rect` when `texture_atlas` is None → the plan's "9-slice composes with a plain rect crop" claim is CONFIRMED.
- **Silent missing-texture-key gap shared by Icon + Textured.** Both arms resolve `catalog.textures.get(key).map(load).unwrap_or_default()` — NO warn, does NOT skip the bar (spawns with empty `Handle::default()`). CLI `validate.rs` cross-checks foliage `leaf_texture` and world_stat_bar `stat_key`, but NOT the style's `icon_sheet`/`texture_sheet`. So a typo'd texture key is caught NOWHERE (silent empty bar). The `Textured` plan explicitly promised "warn! once and skip"; implementation inherited Icon's silent pattern instead. Fix both together: add validator cross-check for style texture keys + warn+skip at runtime.
- **`StatWidgetSpawnCtx` reuse was sufficient** — Icon already added `asset_server`/`asset_catalog`; Textured needs only those (no meshes/color_materials/atlas_layouts), reused as-is, nothing missed. `bg_color` is now a MULTIPLY-tint on the textured track layer (vs. flat color for Ascii track-text / Pixel bg-quad; ignored by Icon) — shared color fields now carry style-specific semantics (4-style overload; manageable, documented, watch as enum grows). `spawn_world_stat_bar_widget` is now 4 arms (~310 lines); anchor+rank-loop+WorldLabel+WorldLabelRank/Hidden+LevelEntity boilerplate duplicated across Pixel/Icon/Textured — the plan's "revisit abstraction once all three ship" condition is now MET; extract a shared `spawn_bar_anchor` helper.

**deny_unknown_fields inconsistency in WorldStatBarStyle (caught 2026-07-17):** the enum itself and its `Ascii`/`Pixel` struct variants do NOT carry `#[serde(deny_unknown_fields)]` — only the outer `WorldStatBarDef` struct does. New variants (Icon/Textured) should MATCH the existing variants (no per-variant attribute) for consistency. `world_icon_stat_bar.md`'s schema section incorrectly claims to add it to `Icon` — would introduce inconsistency; flag for correction if Icon is implemented.

**Nameplate shipped (reviewed ~2026-06-25) — two non-obvious facts:**
- The nameplate **anchor is a top-level (unparented) `WorldLabel` entity**, deliberately NOT a child of the tracked entity (same reasoning as `target_indicator` — avoid inheriting animation/scale transforms). Consequence: the anchor + Text2d + per-bar Mesh2d/ColorMaterial are NOT freed by `Action::Despawn` of the tracked entity; only `world_label_screen_pos_system` hides the orphan, and `LevelEntity` cleanup frees it on the next `LoadScene`. This is a real per-entity leak in wave/respawn scenes. Correct fix is a `RemovedComponents<NameplateTag>`-driven cleanup system that despawns `NameplateAnchor.0` — keep the anchor unparented, do not parent it to fix the leak.
- **Two-writer `Visibility` hazard:** both `nameplate_visibility_system` (policy: distance/faction) and `world_label_screen_pos_system` (on-/off-screen projection) write the anchor's `Visibility`. As shipped, the policy system only ever force-Hides and relies on run-order (`.after(world_label_screen_pos_system)`) + the projection system to re-Show. This is a fragile implicit contract — re-show lags one frame and breaks if a third writer or reorder appears. Preferred design: a `NameplatePolicyHidden` marker the projection system ANDs against, so the two concerns don't both write the same component.
- Spawn-condition predicate `nameplate != Some(false) && (show_nameplates || nameplate == Some(true))` was copy-pasted across 5 spawn sites — same divergence anti-pattern `tag_spawned_entity` was created to kill. Flag for extraction into one shared helper.
