**(Superseded once D3 merges: `runtime/schedule.rs` adds GameplaySet/EmitSet/GameStreamSet; the paragraph below is the pre-D3 state.)** **This codebase has zero `SystemSet`s and zero `ScheduleBuildSettings`/ambiguity detection** (verified 2026-09-14: `grep -rn "SystemSet\|configure_sets\|in_set(\|ambiguity_detection" crates/ironhold_core/src` returns nothing). Every ordering constraint is a bare `.before(some_fn)`/`.after(some_fn)` against a concrete system function's `SystemTypeSet`. `lib.rs` alone has ~8 separate `.before(fsm_interpreter_system)` edges (spawn_scene_v2, global_input, unclaimed_gamepad_trigger, the stat chain, audio_state, interactable, the action-bar chain, …) — these used to target `message_interpreter_system` (the `rules.ron` interpreter, first in the chain) until it was removed outright in `rules_to_state_machine_consolidation` (2026-09-28); re-anchored onto `fsm_interpreter_system`, now first.

**Why:** it's the lowest-ceremony mechanism and it's the established convention — a new `.before(fn)` edge is *consistent*, not a smell in isolation. The smell is the aggregate: a `PipelineSet::PreInterpreter` set would collapse those ~8 edges into one named contract.

**How to apply:**
- Adding a `.before(concrete_fn)` edge is the right call for a targeted ordering fix here; don't demand a `SystemSet` for a single edge. Do note the two costs: (a) the constraint lives on a function identity, so it silently evaporates if that fn is renamed/re-registered/wrapped, and (b) it only names *one* consumer, so it under-specifies an invariant that actually has several consumers.
- **Transitive edges are load-bearing and invisible.** E.g. targeting is ordered before both interpreters *only* via `targeting → action_bar_input_system → (ActionBarPlugin's own `.before(fsm_interpreter_system)`)`. Delete the middle edge and the outer one vanishes with no compile error and no test failure. Always trace two hops when reviewing an ordering change.
- **`.before()`/`.chain()` between systems that already conflict on data costs zero parallelism.** Check the param lists first: if both take `ResMut<X>` (or `&mut C` vs `&C` on the same component), the executor was already serializing them and the edge only picks *which* order. This was true for all of `click_select_system`/`tab_targeting_system`/`target_auto_clear_system`/`action_bar_input_system` (all touch `PlayerTarget` + `MessageWriter<GameEvent>`). Say so explicitly when someone asks about the perf cost of a `.chain()`.
- **An ordering fix is a WASM behavior change, not a no-op.** Native runs Bevy's multi-threaded executor (order varies run to run); wasm32 runs the single-threaded executor, where unconstrained systems execute in topological/insertion order — i.e. plugin registration order in `lib.rs`. So web already had a *stable* order, and adding an edge can invert it on web while merely de-randomizing it on native. Flag this for the playtest checklist and for screenshot baselines whenever an ordering edge lands.

**Event-order hazards are per message *type*, not across types** (verified 2026-10-01, HashMap-order audit triage): both interpreters collect `UiEvent` first, then `GameEvent`, then `SceneEvent` (`fsm_interpreter.rs:35-52`, `entity_fsm_interpreter.rs:24-40`). So an ambiguity between a `UiEvent` writer and a `GameEvent` writer cannot change FSM outcomes; only same-type writers racing each other can (UI: `button_system`/`icon_button_click_system`/`global_input_system`/`unclaimed_gamepad_trigger_system`; Game: stat chain/`interactable_system`/`tick_delayed_events_system`/action-bar+targeting chain). Fix = one deterministic `.chain()` per type inside a named set, plus a *filtered* conflict test on `Messages<UiEvent>`/`Messages<GameEvent>`/`ActionQueue` — not blanket `LogLevel::Warn` (floods with zero SystemSets). Clippy is NOT part of the workflow gate, so a `disallowed-types` lint alone is decorative; a source-scan integration test (ron_lint-style) is what actually gates.

See [[schedule-update-vs-fixedupdate]] for which systems live in which schedule, and [[flaky-test-trust-gate]] for the ambiguity-detection follow-up.

**D3 plan-review facts (2026-10-02, bevy_ecs 0.18.0 source verified):**
- `ScheduleGraph::conflicting_systems()` is computed on EVERY build regardless of `ambiguity_detection` (schedule.rs:1201, unconditional) — a filtered-conflict test needs no `ScheduleBuildSettings`, just `Schedule::initialize` then filter the `(SystemKey, SystemKey, Box<[ComponentId]>)` triples by `world.resource_id::<Messages<T>>()`.
- `Schedule::initialize` MOVES systems (and their `access`) out of the graph into `executable` (`pub(super)`); to inspect per-system access, call `graph_mut().initialize(world)` first and read `graph().systems` before building. `systems_in_set` errors until built.
- Edges to a `SystemTypeSet` with 2+ instances are a build error (`SystemTypeSetAmbiguity`) — `stat_effective_value_system` is registered twice in `lib.rs` (pre-interp stat chain + post-executor chain), so nobody may ever `.before/.after(stat_effective_value_system)`.
- `ActionQueue` has THREE direct non-interpreter pushers despite src/CLAUDE.md's "only interpreters push" rule: `dialogue_tick_system` (ordered), `despawn_timer_system` and `resolve_pending_behaviors_system` (both UNORDERED vs the interpreter/executor → FIFO position + same-frame/next-frame execution is executor-chosen).
- A schedule test only sees systems registered in the test App; anything left inline in `start_app` is invisible to it — pair it with a source-scan.

**D3 refresh facts (2026-10-14, at c6c4161, bevy_ecs 0.18.0 source verified):**
- The Update block lives in `GamePlugin::build`, and `tests/support::setup_test_app()` installs `GamePlugin`, so a schedule test sees EVERY system. The "test is blind to inline start_app registrations" premise (which justified D3's source scan) was wrong; an access-based membership check over the full graph replaced it (D-f).
- Set-level `run_if` is evaluated ONCE at the first member's turn, cached (`evaluated_sets`), and skips all members on false (single_threaded.rs:86-106). Never put a condition on a set whose members span the executor; this is why the `PlayerInputSet.run_if(sim_running)` idea was dropped (D-g).
- `conflicting_systems()` uses system access only; `run_if` condition access (e.g. `sim_running`'s `Res<SimClock>`) is invisible to it. Check `Systems::get_conditions(key)` separately.
- `SimClock` writers are hidden in SystemParam bundles (`SceneV2Params`, `SceneStateParams`); grep on signatures misses them.
- Single-threaded executor order = Tarjan-SCC toposort over insertion order AND edges: adding any set/edge can reorder unrelated unconstrained systems on web. "Register at the exact spot" minimises churn but does not freeze web order; diff the SingleThreaded executable order before/after.
- `*_ignore_deferred` variants exist for sets; a new edge from a Commands-using system otherwise adds an auto sync point. Sync nodes are shared per dependency distance across the schedule, so one new upstream sync shifts unrelated hidden orderings; a before/after order diff is never clean. A new chain whose members have Commands needs `chain_ignore_deferred()` to avoid extra syncs (the flush moves to the next normal edge).
- Schedule-test gotchas (debug-detective, 2026-10-14): `Schedule::initialize` also moves run conditions (system AND set) out of the graph; exclusive/`AccessConflicts::All` conflicts have an EMPTY component list; assert conflicts ⊆ allowlist (shared syncs order pairs incidentally); `warnings()` includes third-party plugins.
- A gate-inventory predicate on "reads input + mutates player Transform" must except dt-scaled systems (`camera_orbit_system`): Time<Virtual> already freezes them.
- Non-interpreter message readers race writers too: `npc_hit_relay` (vs apply_sim_clock/stat_threshold), `preload_audio`/`preload_decals`/`clear_pool_on_scene_unload` (SceneEvent).

**D3 post-implementation review (2026-10-14, feature/pipeline_system_sets, uncommitted at review time):**
- Accepted deviation: `GameplaySchedulePlugin` only `configure_sets`; members tag `.in_set` at their ORIGINAL registration sites (lib.rs + ActionBar/TargetingPlugin) to keep node insertion order (web tie-breaks). Idiomatic Bevy; the membership manifest is the test's expect-table, not the plugin. Cost: re-homing to FixedUpdate (fixed-tick P3) touches every site. Plugin-before-members order is tie-break hygiene, not correctness.
- Read-order trap for docs: interpreters read ALL UiEvents first. No UiEvent writer exists outside EmitSet::Ui (only lib.rs/input.rs), so there is no UI carry-over — this frame's key/pad/button events precede the previous frame's carried-over GameEvents. A single numbered "carry-over first" list mixing streams is wrong.
- Test-helper soundness: `has_resource_read/write` return true for `reads_all_resources` (exclusive systems) → conservative; `world.resource_id` None silently vacuates a check (expect it); short-name membership conflates same-named fns.
- `<!-- b:NNN[.rule] -->` anchors in folder CLAUDE.md files are audit-tracked (`tools/claude_md_audit.py`); edits that replace a neighbouring paragraph easily delete the next block's anchor.
