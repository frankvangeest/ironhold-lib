There are FOUR player-entity construction sites that MUST be kept in sync. Any feature that changes player spawning (local co-op, character select, respawn, possession) must account for all four or players diverge silently. See [[scene-prefab-boundary]] and [[core-architectural-decisions]].

**The sites (verified 2026-07-03):**
1. **GLB collector** — `scene_loader.rs:164` `player_config: Option<PlayerConfig>`, assembled at `:626`. SINGULAR: overwritten each player-tagged entity, so a 2nd GLB player discards the 1st.
2. **Primitive collector + inline spawn** — `scene_loader.rs:166` `primitive_player: Option<(tuple)>`, set at `:244`, spawned INLINE at `:699`–`:862` (builds its own `CharacterController` + `OrbitCamera`; does NOT use `PlayerConfig` at all). Also SINGULAR. **A primitive-capsule demo uses THIS path** — easy to miss because it's not a `PlayerConfig`. `Vec<PlayerConfig>` alone does nothing for primitive players.
3. **Dynamic spawn** — `action_executor.rs:148`–`173` assembles a 3rd `PlayerConfig` literal for `Action::Spawn` on a `tags:["player"]` prefab (character-select). One player per action, so it doesn't break count, but any new `PlayerConfig` field must be populated here too.
4. **`spawn_player_entity`** — `entity_spawner.rs:491`, the shared GLB spawn fn; consumes `QueuedSpawn.player_config` (`mod.rs:173`) and `PendingPlayerConfig` (`mod.rs:346`, NOT 868). GLB non-terrain path calls it directly (`scene_loader.rs:873`); terrain path defers via `PendingPlayerConfig`.

Note: `PlayerConfig` is assembled by hand in TWO literals (`scene_loader.rs:626` + `action_executor.rs:155`); a shared `assemble_player_config` helper was proposed and DROPPED in `claude_suggestions.md:71`. Land it BEFORE adding any new `PlayerConfig` field.

**UPDATE (local co-op Stage 1, 2026-07-04, uncommitted at review time):** the shared helper landed — `assemble_player_config` now lives in `entity_spawner.rs` and both site 1 (scene_loader GLB collector, now `player_configs: Vec<PlayerConfig>`) and site 3 (action_executor dynamic spawn) route through it. Site 4 was split: `spawn_player_entity` (single-player, own OrbitCamera) + `spawn_players_and_camera` (1+ players; 2+ share one PartyOrbitCamera) both delegate to a private `spawn_player_entity_core` for model/physics/metadata, so no per-call-site drift. Terrain path `PendingPlayerConfig(Vec<PlayerConfig>)` now routes through `spawn_players_and_camera` too. Site 2 (primitive inline) deliberately left single-player-only. Verified `spawn_player_entity` single-player behavior is byte-identical for the three existing callers (it just wraps core + one camera). This is the reference pattern for future player-spawn features.

**Detection:** player prefabs are identified by `components.tags.contains("player")` (the `TAG_PLAYER` magic-string constant in scene_loader.rs). Same stringly-typed mechanism for `flycam`.

**Load-bearing components on the player** (omitting any silently breaks movement): `CharacterController`, `SpeedMultiplier(1.0)` (player_movement_system filters on it — caused a real past bug on the GLB path), `LocomotionState`, `AnimationRequests`, `ActiveOverride`, `RigidBody::Dynamic`, capsule `Collider::compound`, `LockedAxes::ROTATION_LOCKED`, plus `tag_spawned_entity` metadata. Camera is a SEPARATE top-level entity with `OrbitCamera{target: player}` — NOT a child.

**Known inconsistency — RESOLVED in v2 (2026-08-06, feature/player-model-unification-v2):** GLB players used to omit the zero-`Friction` component the primitive and NPC paths include. The `if matches!(model_source, Primitive)` guard was deleted; `Friction{0.0, Min}` is now inside the shared post-dispatch insert tuple in `spawn_player_entity_core` (13-element tuple, still under Bevy's 15-element Bundle limit). No new schema field; `idle_drag` is the documented fallback.

**Rule for new player-spawn paths (e.g. runtime `Action::Spawn` of a player prefab):**
- Factor `PlayerConfig` assembly into ONE shared helper; do not copy the field-by-field construction. The codebase has repeatedly been bitten by per-path divergence (see `tag_spawned_entity` consolidation history).
- Detect the player tag in the ACTION EXECUTOR, not `drain_spawn_queue_system` — the drain system intentionally has no catalog access (`QueuedSpawn` carries pre-resolved data).
- `drain_spawn_queue_system` has no scene context, so tonemapping for a runtime-spawned orbit camera must come from a resource set at scene load (mirror `LoadedSpawnPoints`) or fall back to `Tonemapping::AcesFitted`.
- A no-player scene spawns a "Default Camera"; runtime-spawning a player adds a second `Camera3d`. The dual-camera contract must be decided explicitly.

**How to apply:** When advising on any feature that spawns a player (character select, respawn, possession), insist on the shared `build_player_config` helper and the executor-side detection. Watch for terrain timing: scene-loader defers player spawn via `PendingPlayerConfig` until terrain is ready; a runtime spawn does not, so on terrain scenes the player may spawn before the ground collider exists.

**Single-path "spawn N players (SP = N=1)" convergence — root cause analysis (advised 2026-07-17):** The GLB side is ALREADY ~unified (sites 1/3/4 → `assemble_player_config` + `spawn_player_entity_core`; `spawn_player_entity` is just the N=1 branch of `spawn_players_and_camera`). The remaining divergence is site 2 (primitive/capsule inline, `scene_loader.rs:706-870`). **The actual blocker is model-source polymorphism, NOT camera assignment.** Camera is already centralized (`spawn_players_and_camera` does party/split/single); the primitive path merely re-inlines the N=1 OrbitCamera spawn. What's hardwired is `PlayerConfig.model_path: String` → `model_spawner.spawn_instance` (GLB only); a primitive player carries shape+PrimitiveParams+children and builds its body via `build_primitive_mesh`/`primitive_material`/`spawn_primitive_children` instead. Same GLB-vs-primitive fork exists for ALL entities (`spawn_prefab_instance` handles GLB; scene_loader handles primitive separately) — it's not player-specific. Keystone fix to collapse site 2: add a `PlayerModelSource` enum (`Glb(path)` | `Primitive{shape,params,children}`) to `PlayerConfig`, dispatch inside `spawn_player_entity_core`, delete the inline block. Planned in `planning/features/player_model_source_unification.md`.

**Plan-review of that keystone (2026-07-17, verified against source) — the real cost the plan understated:**
- **CORRECTION to the "attach_prefab_features auto-fix" note above (it was WRONG):** `attach_prefab_features` is NOT called on EITHER player path — neither GLB nor primitive. It is not primitive-specific and unification does NOT auto-fix it. Player `StatMap` comes from a SEPARATE direct call to `build_stat_map_from_templates` in `spawn_player_entity_core:838`, not from `attach_prefab_features`. The genuinely-differing fields between the two paths today are only: `PlayerIndex`, `StatMap`/`stat_templates`, `material` (`PendingMaterialOverride`), and the single-primitive-player structural cap (`primitive_player: Option<tuple>`, not a Vec). The plan correctly scopes attach_prefab_features OUT.
- **RESOURCE-THREADING BARRIER (this is why it's "riskier"):** primitive body construction needs `&mut Assets<Mesh>`, `&mut Assets<StandardMaterial>`, `&Assets<CustomMaterial>`, the per-scene-load BUILT-materials map (`mats.built.0`), `project.primitive_default_color`, and the asset+prefab catalogs (for `spawn_primitive_children`). `spawn_player_entity_core` has NONE of these (only `commands, asset_server, fixes, model_spawner, player_config, project_root, registry`). Moving primitive construction into it forces threading all of that through `spawn_player_entity_core` + `spawn_player_entity` + `spawn_players_and_camera` + the two Bevy SYSTEMS `spawn_player_when_terrain_ready` and `drain_spawn_queue_system` — the last two currently have zero `Assets<Mesh>`/material access. The built-materials map is worst: it's built fresh in `spawn_scene_v2`, not a Resource, so terrain-deferred and dynamic paths can't see it. This is NOT "a visibility bump + a match arm."
- **Terrain timing change:** folding primitive players into `player_configs: Vec` routes a primitive player in a TERRAIN scene through the deferred `PendingPlayerConfig` path (`scene_loader.rs:873`), where today it spawns inline immediately — a real spawn-timing/behavior change.
- **`Action::Spawn` rejects primitive players TODAY (`action_executor.rs:111`):** it does `asset_catalog.models.get(&prefab_def.model)` and `continue`s with a warn if not found. A primitive prefab's `model` is `""` → bail before `assemble_player_config` is ever reached. So the plan's "character-select is a no-op change, verify" task is FALSE — dynamic primitive players need the handler changed too.
- **Dispatch discriminant correctness:** the plan proposes `prefab.shape.is_some() || !prefab.children.is_empty()` vs non-empty `prefab.model`. This MISCLASSIFIES a primitive player prefab with `shape: None` AND empty `children` (legal — `scene_loader.rs:251` defaults to `PrimitiveShapeKind::Capsule3d` via `unwrap_or`). Dispatch on `prefab.kind == PrefabKind::Primitive` instead — matches how scene_loader actually discriminates today.
- **CONFIRMED correct in plan:** `PlayerConfig` is never RON-deserialized (single `PlayerConfig{}` literal at `entity_spawner.rs:979`; no `from_str`/asset loader; the `#[derive(Deserialize)]` is vestigial) → schema change is truly additive/zero-migration. Visibility claims accurate (`build_primitive_mesh`/`spawn_primitive_children` private, `primitive_material` already `pub(crate)`); `pub(super)` works — proven by `resolve_jump_velocity` (already `pub(super)` in scene_loader, imported by entity_spawner). WASM/perf impact: none (spawn-time only).

**Zero-`Friction` on the player collider is NOT a cosmetic one-liner (v2 plan-review, 2026-08-01).** Post-v1 there is no separate "GLB collider construction site" — `Collider::compound` is inserted once in `spawn_player_entity_core`'s shared post-dispatch block (`entity_spawner.rs:970`), and the primitive-only `Friction{0.0, Min}` sits right below it behind an `if matches!(model_source, Primitive)` guard (`:984`). "Add it to GLB too" = delete that guard, not add a line elsewhere. **The real risk is slopes, not cube edges:** `CoefficientCombineRule::Min` outranks Rapier's default `Average`, so 0.0 wins against *any* surface — including the terrain trimesh (`terrain.rs:111`, no `Friction` component → default 0.5/Average). `player_movement_system` writes `velocity.linvel.x/z` directly every `FixedUpdate` tick (idle: `*= idle_drag`, default 0.8), so friction is near-irrelevant while moving and only ever mattered for (a) snagging on vertical faces and (b) *holding position while idle on an incline*. Removing it makes an idle GLB player creep downhill (rough steady state ≈ 5·g·sinθcosθ·dt). `quick_scene` is the live case: GLB `player_warrior` on a 128px×4 = ~512u fbm terrain with 30u max height. Zero-friction precedent (NPCs at `entity_spawner.rs:304`, `scene_loader.rs:410`/`:629`; primitive players) is entirely AI-driven or flat-ground bodies — no human-controlled body has ever run zero-friction on terrain. Any playtest that only checks a flat demo room will greenlight a `quick_scene` regression.

**v2 code-review outcome (2026-08-06) — the blast radius is NARROWER than the v2 plan-review above assumed, and there is a direct precedent the plan-review missed:**
- **Only FOUR `RigidBody::Dynamic` sites exist in the whole engine**: player (`entity_spawner.rs:969`) and three NPC capsules (`entity_spawner.rs:292`, `scene_loader.rs:401`/`:620`). All three NPC sites ALREADY carry `Friction{0.0, Min}`. Every other collider in the engine is `RigidBody::Fixed` (terrain `terrain.rs:137`, static primitives `entity_spawner.rs:226`/`scene_loader.rs:531`/`:2960`). There are **no dynamic props and no kinematic bodies**, so removing player friction cannot break crate-pushing, platform-carrying, or any prop interaction — the ONLY interaction class that changes is player-vs-static-geometry. Check this inventory before accepting any "friction/physics-material change is risky" claim.
- **The "no human-controlled body has ever run zero-friction on terrain" framing was right but incomplete:** `quick_scene`'s `giant_npc` IS a zero-friction/`Min` dynamic capsule standing on that same fbm terrain, and `NpcDef.drag` defaults to **0.8 — the exact same value as `MovementConfig.idle_drag`**, applied the same way (`npc.rs:430` and `player.rs:240` both do `linvel.x/z *= k` per FixedUpdate tick). So the player's post-v2 configuration is structurally identical to a body that has shipped on sloped terrain for months. Strongest available evidence the fallback is adequate.
- **Combine-rule math confirmed from rapier source** (`dynamics/coefficient_combine_rule.rs`): priority is `ClampedSum > Max > Multiply > Min > Average` via `rule1.max(rule2)`, so `Min` on the player beats the terrain's default `Average` → effective friction `min(0.0, 0.5).abs() = 0.0` against *everything*. Creep equilibrium ≈ `d/(1-d) · g·sinθcosθ · dt`; at `d=0.8`, 64 Hz FixedUpdate, 20° slope ≈ 0.2 m/s.
- **`idle_drag` is NOT gated on `loco.is_grounded`** (`player.rs:239-241` — it's the plain `else` of the move-input check). So "lower `idle_drag` to fight slope creep" also removes airborne XZ momentum after releasing input mid-jump. The knob works but is overloaded; the clean engine fix if the regression ever ships is gating the drag on grounded (which also makes `idle_drag: 0.0` a usable hard-stop).
- **No RON path to collider friction exists anywhere**: all four sites hardcode `0.0/Min`, static geometry takes Rapier defaults. A designer cannot author a slippery-ice or sticky-mud surface. Correct to defer, but this is the real data-driven gap if physics materials are ever requested.

Note: code-path convergence ("MP with 1") is a maintainability win but is orthogonal to actual netcode readiness — see [[determinism_networking]] (Rapier float divergence + SimClock are the real MP blockers), don't conflate.

**FIFTH spawn site — hot-join (`local_coop_hot_join_leave.md`, reviewed 2026-07-20, feature branch uncommitted):** `Action::JoinPlayer` (no payload) grows an already-`Grid`-split scene live, up to `MAX_SPLIT_PLAYERS`. Follows the reference pattern cleanly: executor arm resolves config via `assemble_player_config` + overrides `PlayerIndex` to the target slot, pushes `QueuedSpawn{is_hot_join:true}`; `drain_spawn_queue_system`'s new `is_hot_join` branch calls `spawn_player_entity_core` (camera-less) + `spawn_split_camera_for_player`. GLB-only (site-2 primitive path untouched, consistent with all local-coop scoping). New `spawn_split_camera_for_player` helper is a clean extraction of the `Grid` loop body — behavior-preserving.
- **`ActiveSplitSlotCount` is now a TWO-WRITER resource** (was write-once at scene load): executor reads it (`Res`, in `SpawnParams`) as scope guard + slot base; `drain_spawn_queue_system` is the SOLE mutator (`ResMut`) incrementing +1 per hot-join spawn. This split is SOUND, not a race — but its correctness rests on THREE invariants spread across three files: (1) executor `.chain()`ed before drain in `lib.rs` Update; (2) executor computes `next_slot = slot_count + (count of unflushed is_hot_join entries in pending_spawns)` so same-frame double-joins and cross-frame drain delays never collide; (3) `pending_spawns` is cleared on `LoadScene` (`action_executor.rs:51`) so stale entries don't corrupt the count across reloads. Any future change to system ordering, a second hot-join enqueue site, or the pending-clear would silently break slot assignment. When advising on v2 (leave/renumber) or any runtime camera-count mutation, treat these three as a load-bearing invariant set and recommend consolidating the reasoning into one comment at the executor arm.
- `split_screen_viewport_system` (camera.rs) reflows ALL slots each frame from `ActiveSplitSlotCount` — so incremental add needs zero viewport-system change. Minor transient: drain sets the count immediately but the new camera spawns via deferred commands, so the viewport system can see "N cells, N-1 cameras" for one frame → one empty quadrant (clear color), self-correcting. Strictly better than the rejected despawn-and-rebuild flash.
